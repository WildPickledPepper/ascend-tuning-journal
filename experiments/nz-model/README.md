# BF16 NZ 整模型测试：未采用，已恢复 ND

本次仅增加官方 `--additional-config '{"weight_nz_mode":2}'`，保持 6 号卡单卡、BF16、MTP 单候选、主模型 FULL_DECODE_ONLY/[2]、上下文 4096、并发 1、batch token 512。7 号卡基线一直保留。未改写或编译内核。

## 实测结果

同一 6 号卡，依次测 ND 与 NZ。两个提示各重复 4 次，每次固定输出 128 token，temperature=0、seed=42、关闭思考。预热后正式测速关闭 profiler；另采相同 32-token 请求。

| 项目 | ND | NZ |
|---|---:|---:|
| 生成速度中位数（token/s） | 31.207 | 29.053 |
| 128-token 请求时间中位数（s） | 4.464 | 4.771 |
| 首 token 中位等待（ms） | 392.919 | 391.090 |
| 草稿接受率 | 85.887% | 85.887% |

NZ 速度下降 **6.904%**，请求时间增加 **6.875%**。接受计数两侧均为 744 个草稿、639 个接受；计数覆盖预热、性能请求和输出检查，不包括 profiler。

8 次性能请求和 3 项数学/Python/翻译检查的 token ID 与文本全部一致，也与之前非 MTP 基线的对应输出一致。该验证仅覆盖所测短提示。

## Insight 后端确认真实执行路径

直接导入编译版后端 9099，以 `operator/statistic` 按形状汇总，再通过 `operator/more_info` 每组取 20 条样本。ND 为 `ND;ND`，NZ 为 `ND;FRACTAL_NZ`，调用名称由 `aclnnMatmul` 变成 `aclnnMatmulWeightNz`，dtype 仍是 `DT_BF16;DT_BF16`。

| 单次 decode 矩阵乘 | ND（μs） | NZ（μs） | 耗时变化 |
|---|---:|---:|---:|
| 门控＋升维 | 287.362 | 305.586 | +6.34% |
| 降维 | 152.136 | 165.872 | +9.03% |

两侧都是 17 次主模型验证轮；两组 FFN 各 1105 次，含 1088 次主模型和 17 次草稿层调用。两组累计时间 **485.645→520.961 ms（+7.27%）**；全部矩阵乘累计 **767.532→840.437 ms**。本次回退有明确的设备执行证据，接受率没有变化。

NZ 导出的是物理分块形状：如 `[320,2176,16,16]` 对应本次对齐的 `[34816,5120]` 权重。分析同时保留物理形状与逻辑形状，避免将它遗漏或误认成新的矩阵乘。此映射仅用于本次可核验的对齐 BF16 形状。

## 结论与限制

权重预排改变布局和 CANN 执行路径，并不缩小每个 BF16 权重。先前独立实验只反复执行两份随机权重的线性层，不能代表完整模型跨层访问的环境。本次实测否定的是“在当前模型上启用这个 NZ 配置可以加速”，不是证明所有硬件与负载都不适用 NZ。现有采样没有进一步证明微基准与整网差异具体由哪一级缓存或内核内部机制引起。

两组都是短请求、按阶段执行，没有随机交叉；已保留全部单次速度和条件。CSV 的 decode 窗口与整网 HTTP 速度分母不同。SQL 使用技能要求的原样 compute_view 宏，以只读 sqlite3 执行 Top20 聚合（当前无 msprof MCP SQL 工具）；该 SQL 聚合包含 Prefill，另行标明。

NZ 服务已停止，6 号卡原 MTP ND 服务已恢复并通过健康检查，7 号卡基线健康。恢复后已启动的完整复测按用户要求停止；没有将其记成完成或发布恢复速度结论。
