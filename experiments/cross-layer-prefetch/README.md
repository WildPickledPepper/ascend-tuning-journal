# 原生MTP7层间时序与跨层预取机会核验

**1638个层间边界均紧密衔接，没有发现大的任务空档。** 仅在“上一层FFN降维结束→下一层首个attention投影启动”之间预取，理想可重叠窗口合计也只占本次解码采样的0.514%。更早与上一层降维并发的方案不能由这个结果排除，但尚未取得真实HBM空闲窗口或加速证据，不能宣称可直接实现显著提升。

本次只读复用已有原生MTP7采样，未启动27B、未重跑基线、未训练或修改内核。不是又一次性能测速。

第一轮第0→1层，从降维kernel开始计时，Insight返回：

| 第0层FFN降维 | 0.00 | 156.54 |
| 残差相加Add | 156.56 | 2.38 |
| AddRmsNormBias | 158.96 | 4.02 |

降维结束156.54，到下层投影163.00，共6.46μs：6.40μs在执行向量任务，仅0.06μs为记录的任务间隙。AddRmsNormBias融合残差更新和下一次归一化，该段有数据依赖，并非可直接删除的等待。

所有1638个边界都有且仅有Add→AddRmsNormBias两个计算任务；查询同时考虑其他stream上更早启动、跨越边界的计算任务，未发现额外覆盖。1637个边界没有MEMCPY_ASYNC，另1个边界叠加一笔2.22μs DMA；无计算间隙因此更不能直接当作设备或HBM完全空闲。这也不代表向量算子自身没有HBM访问。

## 能节省多少：仅对紧邻边界的预取给时间上限

1638段边界共10.0875ms；无计算任务的缝隙合计0.11752ms。解码区间为首个主图MODEL_EXECUTE到最后计算任务结束，共1964.28154ms，包含草稿、验证与采样后处理，不含prefill。主图窗口合计1363.64934ms。

假定只能在降维结束后开始预取，而且向量执行期间HBM带宽完全可用、预取零开销、缓存不被挤掉：**最多将10.0875ms的未来读取工作重叠到这些窗口，占解码区间0.51355%，占主图窗口约0.740%。** 这是假设下的时间重叠上限，不是实测收益，也不保证这10ms均可回收。纯粹消除无计算间隙只有0.00598%的区间量级。

下一层首个矩阵权重分别140MiB或160MiB，而它的kernel中位数136.46μs；6μs边界无法隐藏整个读取过程。不能把一个完整kernel时长都当作预取能省掉的时间。

## 提前到上一层降维内部，能否更好

该思路没有被上述0.514%限制，因为它起步更早；本次也没有证明它无效。但还缺少两项关键证据：

1. **真实的并发带宽余量。** 实际模型降维MTE2占比中位88.5%、范围86.7%～88.8%，Cube活动中位15.3%。这些是每任务、核汇总的活动比例，不能得出“HBM空闲11.5%”、各核在同一时刻空闲，或每段空闲持续多少。PIPE_UTILIZATION没有时序化HBM/L2带宽；此次DB也无这样的硬件计数表。既有[910B2能力实测](../wait-timeline/README.md)已确认真实instrTimeLine不受支持，不能把仿真流水当成上板空闲窗口，也没有为重复这个能力限制再启动模型。
2. **预取内容能存活并被下一层使用。** 此前核对本卡L2为192MiB，下一层首个投影权重140/160MiB，当前降维权重170MiB；两者完整工作集同时超过L2。并非证明所有预取必定被挤掉，但不能默认全部能驻留。L1属于各核当前kernel缓冲，现有两个独立原生MatMul没有跨kernel持久缓冲约定，不能直接假定下一层可以消费上一层L1内容。实际方案需分块与缓存/执行调度配合。

此前[缓存来源对照](../mte2-breakdown/cache-controls.md)证明HBM供数路径有重要成本，不等于证明提前发请求就有带宽接纳它，更不等于证明HBM已达峰值。两种结论不能互相替代。

**当前判断：不优先实施简单的“层结束后预取下一层全部权重”。** 它的可重叠窗口太短。更早、分块、受控的跨层预取仍属于待验证候选，本次没有充分证据承诺收益；应测量其是否缩短下一层投影，同时检查上一层是否被带宽争用拖慢、总轮时是否下降。用户此次授权是核对分析，没有部署该候选或改写NPU内核。
