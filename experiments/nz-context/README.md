# NZ 单算子与整模型差异：搬运已定位，最底层根因仍待确认

此轮仅在 6 号卡独立补采原生算子，没有再跑整套模型基准，没有重启两个模型服务或修改内核。日期 2026-10-19，时间由采集产物核验。

## 硬件数据确认了什么

| NZ 路径 | 单算子 | 整模型 |
|---|---:|---:|
| 升维算子耗时（μs） | 245.538 | 305.586 |
| 升维 MTE2 活动时间（μs） | 232.815 | 282.883 |
| 升维 MAC 活动时间（μs） | 31.799 | 31.799 |
| 降维算子耗时（μs） | 139.640 | 165.872 |
| 降维 MTE2 活动时间（μs） | 116.032 | 140.864 |
| 降维 MAC 活动时间（μs） | 22.879 | 22.812 |

这些是分别采样的每组平均值；不同流水活动可以重叠，不能将其时间直接相加。升维主差额位于读取/搬运，计算本体没有相同幅度的膨胀。整模型统计含 64 主层和 1 草稿层；进一步拆分两种 Model ID，主层与草稿层 NZ 都比此单算子慢。

直接导入编译版 Insight，`operator/statistic` 与 `operator/more_info` 核验了形状、dtype 和格式。再以 CSV 的设备开始时间＋stream/task ID 精确对应 `task_time.csv`，确认原生内核入口名称一致：升维 `MatMulV2_NDNZ_ND_FP16_FP16_false_true_all_229571`，降维 `..._229585`。两边都是 23 核。名称里的 FP16 是厂商符号的一部分，实际数据仍由输入字段确认是 BF16。**入口相同不等于已经证明运行时 TilingData、地址和全部控制参数相同。**

## 已检验的解释

1. **不同物理卡**：补采在同一 6 号卡仍复现单算子 NZ 较快，不能用原先 6/7 卡不同直接解释差异。
2. **CANN JIT 模式不同**：独立进程实测 `is_jit_compile_false=True`，与安装版 vLLM 的设置一致，没有重复运行相同 JIT 条件。
3. **少量随机权重命中 L2 较多**：通过读取两份其他 512 MiB 权重作为干预。没有把容量假设当作缓存已清空，直接用 `AiCMetrics.L2Cache` 计数核验。升维读命中比例约 0.151%，降维约 1.78%～1.80%，两种读取条件接近；干预后 NZ 优势仍在。因此本次实验不支持将差异归因于单算子权重命中 L2 更高。
4. **随机数据与真实权重不同**：将真实模型第 0、1 层权重复制到同一批 ND/NZ 张量中，断言数据指针不变，保持输入、图和形状。升维随机 ND/NZ 为 288.385/249.455 μs，真实为 287.365/248.220 μs；降维分别为 161.165/141.710、156.915/138.265 μs。真实权重仍保留 NZ 优势，不能用“原来只测了随机权重”直接解释整模型退化。

L2 命中率按两个读端口 hit 总和除以 hit+miss_allocate 总和计算；包含激活等读请求，不冒充纯权重命中率。后端按 startTime 返回，连续重复条件剔除预热，仅保留每 4 次图回放中的最后一次，共 8 个 kernel；干预条件保留 8 个目标 kernel，排除其他大矩阵读。

## 结论边界与工具限制

可确定的执行层原因是 NZ 在整模型中读取/搬运耗时增长，不是同幅度的乘加增长。当前数据尚未证明更底层原因是运行时 tiling、地址映射或某个内存事务配置，因此不将它们写成根因。

`msprof op` 初次过滤表达式被拒绝，修改为通配符后 application/MSTX 采集仍未获得匹配 kernel，未采用这批空结果。随后改用已安装 PyTorch Profiler 的 L2Cache 指标组，再直接调用 Insight 后端取得计数。图回放采集提示缺少 ACL→NPU flow，硬件 kernel/PMU 数据完整，未据此做 CPU API→kernel 关联分析。

此前“独立两份权重不能推广至整模型”仍是有效的结论边界，但不是经过证实的缓存根因；此轮明确保留上述否定证据。后续不能只重复这种笼统解释。
