# 原生MTP六/七/八候选四题对照

用户要求测试6、8候选是否优于当前7候选。只跑与旧基线相同四道GSM8K题，复用此前7候选三轮基线，不跑128题，不使用刚训练但退化的MTP头。

## 受控配置

- 同一张物理6号910B2顺序执行K6、K8，单卡TP1、原生Qwen3.8-27B、BF16权重和SSM、上下文4096、maxseq1、batchtokens512、显存预算0.97、prefix cache关闭。
- vLLM0.27.1/Ascend0.27.1rc1，原隔离runtime不变。主图FULL_DECODE_ONLY、草稿enforce_eager=false。关闭之前独立MatMul替换，不改原始模型权重、NPU内核或共享安装。
- K6一次验证7个位置，捕获[7]；K7旧基线捕获[8]；K8验证9个位置，捕获[9]。改变候选数必须同步调整验证图尺寸，不能把K8跑出图模式后当成纯候选数对照。运行前后核对主/草稿两种wrapper均有实际捕获、对应num_tokens为K+1。
- 原公开SGLang零样本评测器不变，四题、单并发、greedy T0/top_p1/top_k1、2048输出上限、自然结束；完整请求与旧基线一致，包括return_token_ids。每组64token预热后才拍计数快照。
- 正常计时不带profiler。每个候选只有一次四题测速，测完关闭，下一组在同卡启动；最终不恢复旧服务。

## 判断依据

吞吐＝实际HTTP输出token数/公开评测器端到端总时间，包含prefill及请求开销。接受率＝预热后accepted/proposed计数差，验证轮数＝draft计数差，token/轮＝1+accepted/rounds，尾部/EOS口径与HTTP token数可能略有差别。

服务端decode总秒数来自Prometheus request_decode_time_seconds_sum，除以验证轮数得到每轮平均墙钟耗时。它包括框架和设备执行，**不是ms测得的单轮kernel耗时**；不能与此前profile数字直接相减。TTFT同样取预热后四次请求的sum/count。

更换K会改变轮边界和计算形状，也可能改变浮点路径及生成内容，因此逐题列出实际长度和token ID是否与K7相同。不把候选接受率较高直接写成速度较快，也不将单轮四题最快值当成全局最优。

旧基线59.386318token/s为三轮中位数，三次59.111340/59.386318/59.445242；均844输出token、4/4正确。旧基线不是本次同时重测，结果只提供这三个K在同四题上的比较。

## 复现与证据

- [start.sh](start.sh)：由MTP_K生成K+1图尺寸，强制原生模型路径。
- [model_extension.py](model_extension.py)：测速外只读图审计。
- [client.py](client.py)：同四题、预热、前后计数和完整私有响应。
- [controller.py](controller.py)：独立输出、仅清理自身进程树、检查6/7释放；[serve.py](serve.py)为标准vLLM入口。
- [analyze.py](analyze.py)：严格校验请求、源码SHA、K×rounds=proposed、逐位置和=accepted及主/草稿图，输出过滤证据。

原始回答、token IDs、日志、服务器路径和进程信息不入库；只有汇总和必要代码提交。训练模型未参与本次推理。


## K6已完成的结果

K6为58.460472token/s、844token、14.437105秒、4/4正确；相对K7旧中位数59.386318下降约1.559%。四题长度仍137/44/575/88，题目/完整请求相同；第1/2/4题token IDs完全一致，第3题不一致，不能声称全部token相同。

预热后K6计数182轮、1092候选、674接受，接受率61.7216%、计数token/轮4.703297。K7为171轮、1197候选、681接受，接受率56.8922%、token/轮4.982456。虽然候选接受比例更高，每轮推进更少，验证轮反而增加。

服务端decode/round为75.0888→71.1514ms，减少5.244%；计数token/轮减少5.603%。K6 decode合计12.949557秒，旧K7为12.840187秒；平均服务端TTFT347.238ms对313.717ms。不能将TTFT差额全部归因K，旧基线不是同时重测。综合端到端结果没有变快。

**本次三者中仍是7候选最快，不更改原方案。** K6相对旧中位下降1.559%；K8下降4.042%。这只是同四题及该实现的结果，没有证明所有问题/上下文/并发下K7全局最优。

K8主模型/草稿均实际捕获9位置，图模式通过前后审计。原生权重和生成参数不变，第三题输出593token而非575，其余137/44/88。首、二、四题token IDs与旧K7完全一致；第三题不一致，因此不能说三组做了完全相同数量的输出工作。四题最终答案均得分。

K8实际每轮推进4.994，只比K7的4.982多约0.24%，服务端decode/轮却多约3.75%；单轮收益未覆盖成本。它的175轮也受第三题多18token影响，不把轮数差全部解释为接受率退化。K8整体接受率699/1400＝49.929%，第8位置有42次通过，但不能把这42直接加在旧K7轨迹上：改变K后验证边界、上下文和浮点计算形状均会改变，轨迹已不是同一组轮次。此次未带profiler，不凭这些计数再细分额外耗时来自哪个kernel。

此前基于128题前缀估计K6/K8的token/轮是用于设定盈亏门槛，**不是实测成绩**；当前四题基线自身为4.982，不能与128题的4.591混用。当前实测已经取代本次四题的估计。
