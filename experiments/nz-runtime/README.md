# NZ 单算子与整模型：实际下发参数及工作集对照

本次继续解释 NZ 单算子更快、整模型却更慢。保持 BF16、M=2、物理 6 号卡、原生 CANN；不写或替换 NPU 内核。仅临时记录运行时参数、采集一个 32-token 请求，并做隔离的原生矩阵乘对照，没有重复完整模型测速。

**已验证的解释：同一 NZ 内核，在跨 64 层读取不同权重时，搬运效率下降。分块、格式、地址对齐错误或多读了权重，均不能解释本次结果。** 该结论定位到“工作集与读取上下文影响搬运效率”；没有采集 SMMU/TLB 或 HBM 通道计数，不能把更底层原因直接写成 TLB miss、某个 bank 冲突或硬件缺陷。

## 上板对照

以下是编译版 Insight `operator/statistic` 返回的单次 kernel 均值，单位 μs；硬件 PMU 与原始 CSV 交叉核对。完整数值见[证据摘要](../../evidence/2026-10-19/nz-runtime-comparison.json)。

| 执行内容 | 升维 | 降维 | 每组有效 kernel 数 |
|---|---:|---:|---:|
| 模型实际缓冲区，隔离执行两层及 MTP 层 | 260.44 | 138.59 | 12 |
| 反复读两层，图内共 128 次矩阵乘 | 236.15 | 136.94 | 256 |
| 按 64 层顺序读不同权重，图内同为 128 次矩阵乘 | 293.32 | 165.87 | 256 |
| 完整模型，另采 32 个输出 token | 305.65 | 165.98 | 1105 |

两个 128 次矩阵乘的图都执行 4 次用于 profiling，因而每种形状 64×4=256 次。小工作集反复读第 0、1 层，大工作集按主模型 64 层顺序读取；均按 gate/up、down 交替，只调用原生 `torch.mm(..., out=...)`，不执行 attention、GDN、激活或模型采样。两层 FFN 权重工作集 1,069,547,520 B，64 层 34,225,520,640 B；每轮的总逻辑权重读取字节数相同。

**算子调用数、图长度一致时，扩大不同权重的工作集仍能复现降维几乎全部退化，以及升维的大部分退化。** 完整模型的升维还比 64 层 FFN 图慢约 12.3 μs，这部分没有被本对照完整解释。

| PMU 活动时间，μs | 两层反复读 | 64 层不同权重 | 完整模型 |
|---|---:|---:|---:|
| 升维 MTE2 | 227.700 | 270.103 | 283.071 |
| 升维 MAC | 31.799 | 31.799 | 31.799 |
| 降维 MTE2 | 113.229 | 141.010 | 140.950 |
| 降维 MAC | 22.839 | 22.775 | 22.772 |

另用 `AiCMetrics.MemoryAccess` 单独采集相同两种图：

| 每次 kernel 的计数字段 | 两层反复读 | 64 层不同权重 |
|---|---:|---:|
| 升维 `aic_read_main_memory_datas(KB)` | 348631.099 | 348631.098 |
| 升维 `aic_GM_to_L1_datas(KB)` | 350000.000 | 350000.000 |
| 降维 `aic_read_main_memory_datas(KB)` | 177219.217 | 177219.212 |
| 降维 `aic_GM_to_L1_datas(KB)` | 186592.000 | 186592.000 |

单位沿用工具字段，KB 按该工具的 1024 B 口径换算；保留原值方便核查。计数几乎不变，变的是完成读取所需的时间。它们不能替代 HBM 各通道、TLB 或物理事务明细。最初四个 FFN kernel 的区间没有与其他已记录设备 kernel 重叠；没有据此编造“attention 正在并发抢带宽”的解释。

## 实际 TilingData 与地址

主机端 hook 只观察、原样转发 CANN launch。使用安装版本头文件核验 `aclrtLaunchKernelWithHostArgs` ABI，记录 200 B 参数包、占位映射、160 B TilingData 与设备指针；同时在权重加载完成后记录格式、形状和 stride。没有改共享库、安装包、驱动或计算公式。

| 对象 | 升维 | 降维 |
|---|---|---|
| 原生入口后缀 / tiling key | `229571` | `229585` |
| 完整入口 | `MatMulV2_NDNZ_ND_FP16_FP16_false_true_all_229571` | `MatMulV2_NDNZ_ND_FP16_FP16_false_true_all_229585` |
| 逻辑 M,N,K | 2,34816,5120 | 2,5120,17408 |
| block dim | 23 | 23 |
| TilingData | 160 B | 160 B |
| 对照结果 | 前 152 B 逐字节一致，最后 4 B 均为 `0xa5a5a5a5` | 同左 |

两条入口所在 NZ ELF 的 SHA-256 都是 `f4bd226d4a56698f7e6de39bbd9731855913f010d7a2aa14fd3eddaf285fae5d`，单算子 dump 与模型进程实际加载的 ELF 相同。名字含 FP16，但 profiler 的实际输入类型为 BF16，不代表改成了 FP16。

偏移 152 的一个 uint32 随下发记录变化，语义字段名未核实，不能声称全部 160 B 完全相同。core0 升维仿真的标量载入覆盖到偏移 148 的 4 B，没有读取 152..159；两种工作集同地址对照的前 152 B 也一致。归档的模型进程记录包含每条目标入口各 278 条匹配 M=2、N、K 的下发，含模型启动、短请求和后续隔离图的捕获；不是 278 次解码图回放。

以主模型第 1 层为例，下列地址在原模型捕获、隔离小工作集和 64 层图中保持相同；不是仅比较对齐余数：

| 张量 | 升维地址 | 降维地址 |
|---|---|---|
| 输入 X | `0x131800007e00` | `0x131800076e00` |
| 权重 W | `0x12d3b4a20000` | `0x12d3c9e24000` |
| 输出 Y | `0x131800054c00` | `0x131800012200` |
| X stride | `(5120,1)` | `(17408,1)` |
| W 逻辑 stride | `(5120,1)` | `(17408,1)` |
| W 格式 / storage offset | FRACTAL_NZ / 0 | FRACTAL_NZ / 0 |

同一第 1 层，固定这三个指针后：

| 上板耗时，μs | 小工作集、128 次图 | 64 层工作集、128 次图 | 完整模型 |
|---|---:|---:|---:|
| 升维 | 235.907（128 样本） | 295.820（4 样本） | 310.595（17 样本） |
| 降维 | 131.965（128 样本） | 157.465（4 样本） | 158.693（17 样本） |

因此不是某一份权重恰好分配到慢地址：同一地址的 kernel 也随周围工作集改变而变慢。完整模型按每轮 64 个主模型层＋1 个草稿层提取第 1 层，隔离图按已记录的权重顺序提取；未把模型均值与单一层冒充同一对象。

## 原生 DMA 指令参数

这里是 **原生二进制＋实抓 M=2 TilingData 的 simulator/core0 结果**，不是上板逐条 DMA 时序。使用编译版 Insight `source/api/instructions/dynamic` 确认指令 PC、次数、Process Bytes，并结合原仿真 trace 的寄存器值解析。

| 权重搬运参数 | 升维 | 降维 |
|---|---:|---:|
| 指令 | `MOV_OUT_TO_L1` | `MOV_OUT_TO_L1` |
| `XM` | `0x870001000100` | `0x139000700200` |
| `nburst` | 16 | 32 |
| `burst_len`，32 B 单位 | 256 | 112 |
| 每段有效字节 | 8192 | 3584 |
| `src_stride`，32 B 单位，段间空隙 | 34560 | 5008 |
| 相邻源段起点跨度 | 1114112 B | 163840 B |
| `dst_stride` | 0 | 0 |
| 每条权重指令有效字节 | 131072 | 114688 |
| core0 权重搬运条数 | 120 | 68 |
| core0 权重字节合计 | 15728640 | 7798784 |
| 对应权重小块 N×K | 256×256 | 112×512 |

位段按本机 CANN 9.1.0 `tbe/tik/debug/data_move_intrinsic.py:100` 的移位常量和 `:196` 的拼接逻辑解析；32 B 单位同时与 Insight 返回的 Process Bytes 及 NZ 物理布局交叉核对。`src_stride` 是段后空隙，源段**起点跨度**是 `(burst_len+src_stride)×32`，两者不能混淆。core0 升维对应 6 个 N 小块×20 个 K 小块，降维对应 2×34；其他核的尾块不能一概按 core0 尺寸推广。

输入仍是 ND：升维 core0 一条输入 ND2NZ、20480 B；降维 68 条、每条 2048 B。不能把权重已预排 NZ 理解为所有数据都不再转换。上述参数与相同二进制、相同实际分块一致，未发现模型另用了更大搬运块或另一套 stride。

## 工具限制、失败与恢复

- 最初主机采集器遗漏新 ACL launch 入口，第一次只有张量地址、没有 launch 记录；补齐实际 API 后取得有效记录。编译时缺少 profiling include 的首次构建也未产生有效采集。
- 第一次模型采集启动因环境脚本覆盖 PYTHONPATH，worker extension 无法导入；修正实验启动脚本后重新启动，未把失败启动记为有效实验。
- 上板 TimelineDetail 保存了输入、二进制和 tiling，但指令采集返回 `107001`；不采用其上板指令时序。随后原生二进制 simulator 成功完成两组 kernel，未编译 NPU 优化内核。
- simulator 的 `source/details/baseInfo` 和 `memoryGraph` 返回空内容，不作为证据；有效 `instructions/dynamic` 返回与 trace 交叉验证。
- PyTorch 图回放解析提示缺少 ACL→NPU flow，只采用有效设备 kernel/PMU，未依赖 CPU 下发映射。
- 本次保留了入口、参数、地址、指令和工作集对照证据；**没有证明具体 TLB/SMMU 或 HBM 通道机制，也没有新增整模型加速成绩**。
- 结束时已停止临时 NZ 采集服务，恢复 6 号卡原 MTP ND；7 号卡基线保留。两个服务 health=200，恢复进程不含观察 extension、NZ 参数或 LD_PRELOAD。未重复完整基准。

源脚本是特定运行时的实验工具，需设置私有模型/结果目录；不应直接注入共享或生产进程。仓库仅保留必要代码和过滤摘要，原始 DB、trace、CANN ELF、权重和服务器路径不提交。
