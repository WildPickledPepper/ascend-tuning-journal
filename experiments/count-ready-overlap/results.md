# 同步等待转移与低空隙恢复：6卡结果

**当前采样中的无计算空隙已恢复到0.940%，但未证明显著、稳定的端到端加速。** 同服务四题吞吐只提高0.805%，且只有1/4题更快。不能把采样图里减少的约13个百分点直接当成实际吞吐收益。

保持Qwen3.8-27B、910B2物理6卡、BF16权重/conv、48层FP32 SSM、TP1、并发1、MTP7、同轮动态4096、既有FFN重排/prefill直读/down预取。未改安装源码、权重、图内矩阵计算或NPU内核，未设置默认部署。

## 为什么前移接受数之后，另一个同步增加

源码里有两份不同用途的计数：

- `num_accepted_tokens`用于混合模型状态与输入准备；原逻辑对采样结果中非−1项计数，保留原状态处理及事件。
- `valid_sampled_token_count`用于下一轮序列长度校正。原drafter入口还要处理discard、词表上界和备用token，因此不能无条件拿第一份计数替代。

首次实验只把第一份提前，第二份仍在词表维护之后计算/回传。新脚本把CPU memcpy scope经`torch_to_npu` flow精确连到设备MEMCPY_ASYNC，而不是用CPU同步时长猜拷贝耗时。对上一轮27个稳态衔接，以当轮主图开始为0：

| 第二份计数的时间 | 原顺序 | 只提前第一份 |
|---|---:|---:|
| 设备拷贝完成 | 60.194ms | 60.187ms |
| 实际设备拷贝耗时 | 1.895µs | 1.877µs |
| CPU到达第三个同步 | 62.438ms | 54.104ms |
| CPU在第三同步的等待 | 0.077ms | 6.138ms |

**拷贝没有变慢。CPU更早走到了一个尚未就绪的结果前面。** 原来CPU等第一份时，第二份也完成了；第一份提前后，原先被覆盖的第二条依赖暴露出来。同步等待变长本身不代表新增了同等长度的NPU空闲。

见[逐轮flow证据](../../evidence/2026-10-22/count-wait-exposure.json)和[复算脚本](explain_waits.py)。

## 实际改动与验证

阶段2把原来的`prepare_next_token_ids_padded`放到原始bookkeeping之后、本轮词表维护之前，提前其计算与回传；原草稿入口复用同一对结果，避免重复下发及再次晚回传。两份计数分别保留原有语义，没有简单合并，也没有删除同步或延迟一轮选词。

阶段2每组32题，输出均8764token、逐token一致，吞吐60.795→63.485 token/s（+4.424%）。但这一组原顺序采样Host时间明显偏高：空隙30.907%，不同轮输入准备晚于草稿15.5～42.5ms；不能将它作为稳定基线或把全部差异唯一归因于调度。阶段2CPU准备仍有23个Sub，第二份计数等待虽降到0.087ms，剩余Host工作仍限制衔接。

阶段3针对固定单请求MTP7的实际**AscendGDNAttentionMetadataBuilder**做元数据快路径。仅纯decode、查询[0,8]、7草稿、cache mode=none生效；固定掩码、索引和查询范围复用，状态索引和接受数量仍每轮更新。prefill、其他长度/批量回退原builder。初版接到未使用的上游builder，被“必须真实命中快路径”的检查拦下，未进入测速；修正后保留失败记录。

CPU对照覆盖接受数1～8；真实NPU上两道题的3个实际builder各检查30个字段，含10个Tensor字段及Ascend动态附加的卷积元数据，数值、shape、stride、dtype、device均一致。两道预检的原顺序重复两次可复现，新路径的候选集合和草稿轨迹也逐轮一致；输出137/575token。正式32题关闭诊断，全部逐token匹配已有参考、自然结束、上限2048未触顶。5799次快路径调用、99次固定部分初始化记录在原始审计中。

## 阶段3同服务profiling

同题121输入、前128输出、28次主图及28次草稿图；从首个主图到最后计算任务，排除prefill。Level1、CPU/NPU、record_shapes、Text/DB配置相同，正常Stop。

| 指标 | 原顺序 | 两份计数提前＋元数据快路径 |
|---|---:|---:|
| decode设备窗口 | 2178.685ms | 1894.377ms |
| 无计算区间 | 301.112ms | 17.801ms |
| 无计算占比 | 13.821% | **0.940%** |
| 输入准备CPU墙钟/轮 | 40.932ms | 21.558ms |
| 扣显式Event等待后的准备/轮 | 20.329ms | 11.627ms |
| 接受数量等待/轮 | 20.467ms | 9.789ms |
| 有效token数等待/轮 | 0.079ms | 0.084ms |
| 准备完成−草稿结束 | 晚10.573ms | **早6.423ms** |
| 准备中的Sub调用/轮 | 23 | 2 |
| 主图窗口均值 | 49.720ms | 49.753ms |
| 草稿图窗口均值 | 6.586ms | 6.594ms |

27个稳态衔接中，输入准备全部提前完成，提前量5.816～6.905ms。它能覆盖在词表维护与草稿计算期间，下一主图可以提前排队。两图自身耗时基本不变；优化的是Host准备与衔接。

从依赖上看，下一主图要同时等草稿结果和输入就绪。原路径输入晚了约10.6ms，形成图间空隙；新路径输入已经提前约6.4ms准备好。CPU仍可在NPU忙于主图时等待计数，追求每个同步都为0没有意义。

0.940%接近历史0.922%，但历史采用完整词表/BF16状态等旧配置，不是同一算法的严格对照。这里的主要证据是当前同服务13.821%→0.940%。无计算区间可能包含DMA/同步，不等于整卡完全空闲。

## 为什么真实吞吐仍没有同幅度提升

未开启profiler的同服务四题：

| 指标 | 原顺序 | 阶段3 |
|---|---:|---:|
| 相同输出token | 844 | 844 |
| E2E总和 | 13.506688s | 13.398876s |
| 输出吞吐 | 62.487562 token/s | 62.990356 token/s |
| 平均TTFT | 361.539ms | 407.785ms |
| 每请求平均TPOT | 14.647ms/token | 14.456ms/token |
| 草稿轮数 | 174 | 174 |
| 接受草稿token | 682 | 678 |

吞吐只提高0.805%，仅1/4题更快，TTFT反而变差。两组各一次，保留共享Host和执行顺序波动，不声称稳定提升；输出相同也不能外推为全部草稿轨迹一致。

阶段3完整32题：8764输出，E2E总和136.959323s，吞吐**63.989802 token/s**，平均TTFT343.562ms，TPOT14.479ms/token；1872草稿轮、接受6958token、每轮3.71688。相对近期同卡原顺序32题60.795为+5.255%，但**跨服务、跨时间**，不能代替上述同服务四题对照，也不能声称稳定优于此前64.40 token/s。

又用同题128输出比较开启/关闭采样的客户端耗时：

| 路径 | 开采样E2E | 关闭采样E2E | 开采样的首token后耗时 | 关闭采样的首token后耗时 |
|---|---:|---:|---:|---:|
| 原顺序 | 2.714126s | 2.154604s | 2.106504s | 1.774144s |
| 阶段3 | 2.439895s | 2.146023s | 1.826833s | 1.808692s |

**这些结果说明采样显著扰动了原路径，并放大了Host瓶颈。** 大量小Tensor操作在CPU追踪/record_shapes下更容易使输入准备落到草稿结束之后；减少这些操作，既减少真实Host工作，也大幅减少采样下的额外开销。因此采样图改善很大，未采样吞吐改善却小。

这组128请求各一次，原顺序关闭采样时总采样调用28次（含prefill），开启采样时对应28个decode主图，尾部异步工作/执行轨迹并非完全相同；不能把每一毫秒差值都精确归为追踪开销，也不能从HTTP耗时直接推算未采样的设备空隙。尝试CANN动态附加时目标PID被当前工具拒绝，未得到轻量设备采样，未编造其结果。

当前Host衔接在采样中已恢复充分重叠，真实吞吐没有显著稳定提升的证据。继续仅为降低界面上的空隙百分比而追加Host优化，预期收益有限。本轮不设置默认部署。
