# 首token延迟增加：已有数据追查

**四题中的TTFT增加是真实记录，但尚未证明是优化引入的稳定退化。** 服务端计时将增加定位到「首次调度→第一个输出」这一阶段；无法进一步唯一归因于CPU调度、下发、设备执行或结果回传。第3题499ms的无采样请求没有内部阶段时间戳，其他题的profiler不能替它补出根因。本轮新增NPU请求0，不启动服务、不改推理实现、不自动提交Git。

沿用既有6卡910B2、Qwen3.8-27B、BF16权重/FP32 SSM、TP1/并发1/MTP7、同轮动态4096和既有FFN优化。数据来自同服务原顺序四题、优化四题、随后优化32题、诊断预检和两份既有首题采样。[复算脚本](analyze_ttft.py)、[过滤证据](../../evidence/2026-10-22/count-ready-ttft.json)。

## 增加发生在什么范围

重新读取两组测速前后的Prometheus直方图，所有相关指标计数增量均为4，成功请求4、输入均410token、无prefix cache命中和请求抢占。以四题均值比较：

| 指标 | 原顺序 | 优化版 | 差值 |
|---|---:|---:|---:|
| 客户端TTFT | 361.539ms | 407.785ms | +46.247ms |
| 服务端TTFT | 352.585ms | 397.846ms | +45.262ms |
| 引擎prefill阶段计时 | 323.762ms | 375.673ms | **+51.911ms** |
| 引擎排队 | 0.0285ms | 0.0216ms | −0.0069ms |

客户端、服务端都看到了相近增量，且排队几乎为零，因此证据不支持「只是客户端SSE读取慢了46ms」或「等其他请求排队46ms」。SSE首个空role事件到首个含token_ids事件约0.9～1.1ms，第3题两者同时后移，不能把空role误当首token解释132ms。

这里的**prefill阶段不等于prefill矩阵运算耗时**。只读核对实际运行时`v1/metrics/stats.py`：它用`first_token_ts - scheduled_ts`计时，是首次SCHEDULED到首个NEW_TOKEN的墙钟区间，包含首轮准备、提交和等待结果等工作。服务端TTFT另用API输出处理的时间减arrival_time；客户端再计算HTTP请求开始至收到第一个含token_ids的SSE事件。三者边界不同，不能把它们当完全互斥的纯计算/通信分段。

本轮只读取得计时源码并核对其所在Git commit与实验相同（`6e448d0`），三个文件tracked diff为空、文件SHA256记录在证据中。未修改远端文件或启动模型。四题服务端指标是合计，没有第3题单独的服务端prefill数值，不能声称「132ms全部在第3题prefill算子内」。

## 499ms是否在相同路径下重复出现

| 题目 | 原顺序四题 | 优化四题 | 随后同服务优化32题中的同题 |
|---|---:|---:|---:|
| 第1题（qid0） | 326.002ms | 320.046ms | 378.132ms |
| 第2题（qid1） | 376.693ms | 390.387ms | 349.771ms |
| 第3题（qid2） | 367.458ms | **499.221ms** | **349.785ms** |
| 第4题（qid3） | 376.000ms | 421.487ms | 337.846ms |
| 前四题均值 | 361.539ms | 407.785ms | 353.883ms |

后两列采用同服务、同stage3、关闭诊断和profiler的相同代码路径、相同输入及输出。第3题随后降低149.436ms；第4题降低83.641ms。新增功能没有被关闭，说明「每次都额外增加约132ms」不符合已有观察，也不能仅凭第一次四题均值断言固定12.8%的退化。

这只是已有顺序运行的核对，不是新增随机交错A/B；缓存状态、Host调度和执行时机没有被独立控制，因此不能反过来断言系统性退化完全不存在。诊断预检中的第3题优化TTFT340.155ms、原顺序两次408.908/418.468ms也可见变动，但预检包含候选记录及元数据校验，不混入正式测速统计。

## 首轮代码确实有没有变化

需要修正「只优化decode，所以prefill路径完全不变」这个过强判断：

- **GDN元数据快路径只用于纯decode**：单请求、查询[0,8]、7草稿且非prefill；114-token等prefill调用原builder，并使固定常量在下一次decode重新初始化。
- **两份计数前移属于sample_tokens调度改动，也经过prefill的首次采样**：新增logits/旧草稿快照，提前原状态更新和有效计数回传，再维护词表与下发草稿。不是只改了后续decode的CPU路径。
- 主模型prefill的FFN内核和布局分发没有改。两组四题均256次prefill直读，121/83/114/92各64次，解包回退0；第3题形状此前已在同服务预检执行过。没有发现为了优化而新增一轮prefill或权重解包。

因此，首轮调度存在潜在影响，需要验证；不能单靠「快路径decode-only」排除它。

## 现有详细采样说明什么

两份完整Stop且已解析的Level1/CPU+NPU/record_shapes轨迹来自**qid0、121输入/前128输出**，不是产生499ms的qid2。Text/DB交付件均存在。按首次forward和第一次全词表投影的真实边界重新比较：

| qid0采样指标 | 原顺序 | 优化版 |
|---|---:|---:|
| 首次主模型forward CPU scope | 413.563ms | 424.952ms |
| forward内CPU scope数量 | 15,298 | 15,298 |
| 主prefill至首个全词表head的kernel_details记录数 | 2,265 | 2,265 |
| 上述kernel持续时间累计 | 80.426ms | 80.316ms |
| 首次采样前新增快照clone CPU scope数 | 0 | 2 |
| 上述clone CPU scope累计 | 0 | 0.186ms |
| 首次采样入口→草稿提交结束 | 79.283ms | 76.171ms |

CPU操作名称顺序指纹相同，设备任务的名称/类型/输入shape顺序指纹也相同。支持主prefill计算路径没有膨胀，并显示采样下Host时间可在任务内容相同的情况下变化。CPU scope含嵌套，15,298不等于15,298次独立kernel下发；80ms累计不等于TTFT或整段设备墙钟。新clone的0.186ms是CPU scope、不是完整异步影响上限，不能据此断言新调度绝无副作用。

这些观察没有在首题采样中发现足以直接解释另一次无采样请求+132ms的固定新增工作。不能将「qid0 kernel几乎没变」外推为「qid2肯定也是Host调度问题」；同样不能把profiler本身的几百毫秒Host开销套给未采样的异常请求。

## 当前结论与进一步定位所需证据

后续用户另行授权上板定位和调优，现已完成[首token交付优化及同服务32题对照](../ttft-first-round/results.md)：平均TTFT331.020→304.672ms，吞吐64.704→64.600 token/s，输出32/32一致。历史499ms仍无精确内部证据；以下保留当时只读分析的结论和建议，不能当成后续未执行。

已定位：真实TTFT增加主要落在**引擎首轮处理区间**，不是单纯客户端显示延迟或请求排队；499ms在同代码、同服务的后续同题记录中没有保持。尚未定位：这次首轮内部到底哪一段多花了时间，是否包含首轮调度改动的条件性退化。

若继续上板，最小补证应针对qid0/qid2、同服务、先预热再短序列交错原顺序/优化路径，记录有界的每请求阶段时间戳：入引擎/首次调度、主prefill提交、采样与计数、首次词表reset/repack、草稿提交、首个结果就绪/API首输出。同时用少量异步设备Event区分提交与实际执行，统一在请求结束后回收计时，避免逐阶段synchronize和完整record_shapes再次放大Host开销。先确认慢在哪一段，再决定是否让prefill首轮绕过decode计数前移；当前没有实施这种回退或新测试。

原始请求/回答、token数组、轨迹、完整计时源码及私有路径留数据区；报告只保存数字、逻辑边界和哈希。本轮未操作卡或其他进程，未重新启动服务，也未提交或推送Git。
