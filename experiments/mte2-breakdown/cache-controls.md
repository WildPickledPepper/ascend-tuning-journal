# 修复逐核带宽解析，并用缓存对照定位 HBM→L1 的主要成本

**当前升维的主要限制在 L2 未命中后从 HBM 供数，而不是 ND→NZ 转换或 L1 写入能力本身把速度限制在原来的水平。** 保留原生 ND 内核、实际分块、虚拟权重地址及全部搬运请求，仅改变合成权重的物理工作集，MTE2 从262.652降到113.853μs。与此同时，L2读命中率从0.505%升至81.253%。这是一项数据来源干预，不再只是“搬运活动占比高”的判断。

这是上板受控定位，不是把真实权重压缩到了64MiB，也不是新部署的模型优化；没有新增整模型加速成绩。

## 1. 算子基本信息

device/application，Ascend910B2，物理6单卡，BF16，M=8；升维N=34816/K=5120、权重340MiB，降维N=5120/K=17408、权重170MiB，23核。调用CANN原生`F.linear`，没有重编或替换NPU内核。

使用VMM每64MiB一段映射：full映射不同物理内存，alias64将各段映射至同一64MiB物理分配。矩阵仍按原形状读取完整的逻辑地址范围。实验权重全部为同一个BF16常数，因而这种别名映射保持本例数学结果；**真实模型权重不能这样复用物理存储**。

升维full/alias均预留384MiB虚拟范围，实际访问340MiB；降维均预留192MiB范围，实际访问170MiB。两组同形状实验的虚拟权重地址、key、23核及前152B tiling逐项相同，原始地址留私有数据区。两条路径的输出全部等于对应BF16参考值。

| 升维路径 | 真实大工作集 | 64MiB物理工作集 |
|---|---:|---:|
| ND，运行时转换保留 | 276.279μs | 130.596μs |
| 预排NZ | 239.518μs | 115.296μs |

ND原始三次为275.706/277.286/275.846μs，alias为133.003/130.983/127.803μs；冷源布局差36.761μs，缓存友好时布局差15.300μs。两种布局都对数据是否来自缓存高度敏感。ND/NZ会同时改变指令、读取几何和布局，这两个差额都不是纯转换执行时间，不能与上一张表的缓存差额相加。

### 4）逐核带宽假零的根因与修复

服务器工具版本26.1.0，commit `56632dc4a944410c791538451dc2156a151bd105`。在这一版本：

- 插桩Cube记录索引为`3*b+2`，实际原始记录包含2、5、8……68，共23个核。
- 910B的`Statics`直接用该索引填表，却用PMU核号0……22取表，造成16个假零及其余核错配。
- [修正工具](repair_cube_bandwidth.py)保留原始二进制，在独立CSV中以`(slot-2)/3`关联PMU核号，再按官方字节/活动时间公式重算；四组均得到23个非零带宽，且字节总量与PMU精确一致。
- 修复前公式可复现原CSV全部23行，包括假零；因此不是凭经验替零。修正CSV保留在私有数据区，不覆盖原始测量。

另附[上游源码补丁](msopprof-26.1-cube-block-map.patch)，**没有编译替换服务器原装msprof，也没有修改共享CANN**。已生效的是独立解析修复链。字段标成GB/s，但对应源码用1024³，报告按GiB/s解释。

源码依据：[插桩核号](https://github.com/Ascend/msopprof/blob/56632dc4a944410c791538451dc2156a151bd105/csrc/op_profiling/plugin/utils.h#L228)、[910B汇总](https://github.com/Ascend/msopprof/blob/56632dc4a944410c791538451dc2156a151bd105/csrc/op_profiling/profiling/device/data_parse/metric_data_handler.cpp#L700)、[活跃带宽公式](https://github.com/Ascend/msopprof/blob/56632dc4a944410c791538451dc2156a151bd105/csrc/op_profiling/profiling/device/data_parse/pmu_calculate.cpp#L426)。

编译版后端导入四份MemoryDetail bin，kernel时间均与CSV一致；逐一查询每份23核内存图，92个核的L2读写hit合计与CSV一致。注意Insight内存图显示读写合计，而本文瓶颈表只使用读请求，已按口径分别校验。原bin中的错误动态带宽不会因离线修复CSV而自动改变，分析采用显式修正结果。[查询脚本](backend_memory.cjs)。

## 3. 核心瓶颈 TOP5

1. **主要成本是L2未命中后的HBM供数。** 保留转换和L1写入，缓存来源改善仍让升维MTE2降低148.799μs；相同路径能在更好供数条件下快得多，排除了“转换或L1写口将吞吐固定在原值”的解释。真实模型此前L2命中也很低；340MiB升维权重大于本卡192MiB L2，跨64层复用距离更大。
2. **权重布局影响外存读取效率，但不是全部成本。** 预排NZ在本轮隔离对照中减少约37μs；改变来源的影响约146μs。两种效应存在交互，不能拆成可相加的独立部件时间。
3. **本轮主要差额不由TLB改善解释。** 原始SMMU计数直接反证“alias因TLB更好而快”。这与旧NZ/M2的跨层TLB退化是两个实验场景。

这里定位到缓存未命中后的外存供数路径，**没有声称HBM内存控制器已达标称峰值，也没有细分到DRAM阵列、控制器队列或片上互联的独立周期**。真实模型282.469μs没有被强行拆成三项；上板受控差额与实际模型活动时间分开报告。

## 4. 优化建议 TOP5

- 后续BF16优化应针对实际权重的HBM读取方式和每次读取所服务的有效token数。不要把精力优先放在消掉一个独立“格式转换算子”，本路径的转换融合在原生搬运中。
- 不能部署64MiB别名来替代真实权重；这只是合成常数权重的诊断实验。也不能期待把跨64层的几十GiB权重长期放进L2。
- 若再评估原生NZ/地址组织，须回到当前M8整模型验证跨层地址翻译和吞吐；此前NZ整模型回退记录仍有效，本轮没有推翻或重新部署它。用户已停止自写内核路线。
