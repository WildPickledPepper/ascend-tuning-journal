# 动态词表输出分叉：分轮与状态精度

此前自然第三题在零基311位分叉，575→447 token。本次同一主模型、同一完整草稿投影、同一捕获图与固定mask缓冲，顺序做full→masked→full，复现575→447→575。前后full的token、对齐隐藏向量与预测全部一致，masked与此前小head的447-token输出完全一致。限制候选改变接受长度，足以触发差异；小GEMM数值变化、ID映射不是这一分叉的必要条件。

## 数值机制

GDN算子在一次调用内部用FP32状态连续递推，同时把每个位置的状态按缓存dtype保存。下一轮按接受长度选回相应状态。BF16缓存会在跨轮时产生FP32→BF16→FP32舍入；同一轮内部没有这次读回舍入。不同草稿造成不同接受长度，从而改变舍入位置。权重、主词表没有改变，temperature=0也不能消除计算分组造成的数值差异。

相同已确认前缀下，首个隐藏向量差异在零基输出68位：full是原轮row1，masked是新轮row0，4277/5120元素不同、max abs 0.21875。首个输出分叉在零基311位：

| 候选全局ID | full分数 | masked分数 |
|---|---:|---:|
| 10287 | 21.125 | 21.125 |
| 3481 | 21.0 | 21.125 |

后者形成并列，固定argmax规则选择较小全局ID3481。实际提交token均符合该轮主模型argmax，流式输出与采样ID一致，没有发现验证器错误选择token。

## 单算子因果对照

同样的8个BF16 q/k/v及初始值，一次处理8个，对比拆成4+4或8次1；只改变状态dtype。输出4096元素、末状态65536元素。

| 状态dtype | 分组对照 | 输出不同元素 | 末状态不同元素 |
|---|---|---:|---:|
| FP32 | 8 vs 4+4 | 0 | 0 |
| FP32 | 8 vs 8次1 | 0 | 0 |
| BF16 | 8 vs 4+4 | 797 | 16840 |
| BF16 | 8 vs 8次1 | 1906 | 34001 |

BF16分段输出max abs为0.000244140625，状态max abs为0.00390625；差异紧接分段边界开始。同一分组重复运行逐位一致。**这里的FP32结论仅覆盖单算子**；整网FP32状态修复是后续独立实验，不把它追认成本轮已完成。

## 复现、失败与边界

- `controller.py`只跑既有第三题，正常EOS、上限640；`diagnostic.py`记录实际target输入、隐藏向量和验证前logits；`analyze_traces.py`按prompt+已提交token的精确前缀哈希对齐，不能按草稿轮号直接比较。
- 不用于测速：Host读取、同步、全量logits与trace写盘有额外开销。
- `state_probe.py`配合`run_state_probe.sh`，在CANN设备初始化前选择运行时的custom_transformer算子ABI。最终脚本增加了导入前保护，测量计算主体相同；新增保护后的完整脚本未另跑一次。
- 复用旧编译缓存曾因返回值结构不兼容而启动失败；改独立缓存解决。尝试切换两个独立草稿捕获图曾触发507057，已放弃；最终仅一个图、原地址mask。
- 独立GDN探针曾错误加载另一ABI，出现类型拒绝、零batch无效输出及507035；全部旧结果作废并留在私有失败目录。最终明确选择custom OPP、以FP32能力检查ABI，并验证状态确实写入、重复性和分段前缀一致后，才记录上述结果。没有重置设备或改其他卡。

全量trace、问题、回答、token数组及地址只留私有环境。11:26:48（Asia/Shanghai）确认7卡无进程、8047关闭。后续用户授权FP32修复，见[后续实验](../gdn-fp32-state/README.md)。
