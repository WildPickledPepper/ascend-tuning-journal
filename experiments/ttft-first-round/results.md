# 首token交付优化：TTFT下降约8%，吞吐基本持平

2026-10-22，Asia/Shanghai。用户授权先查清TTFT偏高的原因，再调优并验证吞吐，最后归档Git。最终在**同一7号910B2服务**中对照原有stage3与新增首token交付优化，各32道自然结束GSM8K题。

平均TTFT **331.020→304.672ms（−7.960%）**，最慢 **362.589→327.217ms**，32/32题首token都提前；输出吞吐 **64.704→64.600 token/s（−0.161%）**。保留约64.6 token/s的吞吐，没有证明吞吐提升。32/32最终输出逐token一致，均与此前参考相同；不能把输出相同扩大为所有内部草稿轨迹等价。

## 1. 查到了什么

[此前只读分析](../count-ready-overlap/ttft-analysis.md)把TTFT增量缩小到引擎首次调度至首输出区间。历史499ms请求没有内部阶段时间戳；随后同服务同代码同题约350ms，不能把那次异常唯一归因于一个固定新增操作。

本轮先在6卡做首轮有界计时，完整profiler关闭：原顺序、stage3、仅首轮回原顺序三种模式交错，两道题、正反序各一次。平均TTFT分别约319.731、321.558、320.071ms，未出现稳定的stage3首轮额外退化。首次execute CPU墙钟约230.7～257.0ms，线程CPU接近墙钟；输入准备约1.8～4.7ms；sample_tokens约35.6～39.0ms，其中草稿提交约32.5～35.9ms。观测GC最大约0.920ms，没有找到能解释历史132ms增量的GC停顿。scope嵌套，不能相加；异步Event包含提交间隙，不当纯kernel累计。

结合实际版本源码，确认有两段可以避免的**首输出交付依赖**：

- `AsyncGPUModelRunnerOutput`通常到本轮词表维护、草稿计算已提交后才构造，复制流等待默认流当时的尾部，首token回传被后续工作挡住。
- `EngineCore.step_with_batch_queue`原逻辑优先继续填队列，已有的首prefill结果可能等到再提交一批后才处理。

首token既已被主模型确定，交给客户端并不必然需要等首轮全部草稿计算结束。优化这个交付次序，没有减少主模型prefill的矩阵计算。单独提前复制但不调整Core队列，未显示清晰的TTFT改善；两者需配合。历史499ms精确根因仍不可追溯，本轮改善不能当成对那次异常的完整解释。

## 2. 最终怎么改

原次序示意：

```text
主模型prefill → 首token采样 → 词表/草稿提交 → 原输出D2H
                                  → 继续填队列 → 处理首输出 → 客户端
```

最终路径：

```text
主模型prefill → 首token采样 → 额外的单token D2H → 优先处理首输出 → 客户端
                         ↘ 词表/草稿提交 → 原内部D2H/晚Event → 下一轮准备
```

实现见[first_output_copy.py](first_output_copy.py)。保留原构造函数的所有行为，**内部CPU缓冲和原晚就绪Event不变**；只在`get_output`交付时临时使用独立提前副本，仍调用原转换/过滤逻辑。保留对应GPU张量直到默认流草稿完成和状态流完成，避免提前释放/复用。构造函数11项赋值字段集合检查是schema保护，不声称11个运行值逐项等价。

Core仅变更两处受检查的AST条件：新完整prefill入队后优先交付；队列尾已有完整新prefill时先处理它。正式33次首轮全部命中：新入队24次、已入队9次，包含1次预热及32次正式请求。普通decode的队列填充策略不改，未改安装文件、选词规则、BF16权重或NPU内核。

- 64层packed gate/up、prefill直读、主/草稿down预取保留，主/草稿capture8。

## 4. 一致性与边界

最终32题两组之间及对历史参考均逐token一致，输出总数8764。实际dtype、48层FP32状态、64层packed、prefill解包回退增量0、动态词表缓冲地址、已捕获图和stage3计数对应关系通过审计。33次单token提前复制均被消费，33次首prefill输出均优先处理，pending0；审计时保留1个受Event保护的张量，关闭/卸载时同步清空。

两道预检使用stage0原顺序→stage3加首交付→stage0原顺序。最终答案相同；但前后原顺序自己的完整候选/采样/草稿哈希序列也不重复，故客户端“baseline重复时才断言轨迹相同”的检查在这里**无法给出轨迹等价结论**。这不是全轨迹精度门禁通过。正式32题草稿轮数1870→1872，也没有记录全轨迹；保留这个限制，不声称所有选词过程完全相同。模型策略及选词代码未改，不等于每次异步执行的草稿过程必定相同。

适用范围限所测TP1 greedy、单新请求完成prefill；多并发、长输入跨chunk、logprobs、路由/EP故障检查等未验证。每组仅一轮、顺序运行，未做随机重复，约0.16%的吞吐差值不能赋予统计显著性；无法承诺所有负载都低于某个TTFT。没有重采完整profiling，**不报告本轮新的空隙占比或HBM带宽**。旧0.94%仍是旧采样结果。
