# 接受数量提前：同轮动态词表调度实验

目标是在不改变本轮4096词表、主模型输出和MTP7策略的条件下，把下一轮输入准备依赖的接受状态处理与CPU回传提前。

本轮使用物理6卡，BF16权重/conv、FP32 SSM，TP1、并发1。原顺序与提前顺序在同一个服务、同一套已捕获图中切换。保留已有64层gate/up重排、prefill直接读取和主/草稿down预取，不写NPU内核，不修改安装的框架源码。

原顺序：词表维护 → 主模型采样 → 草稿生成 → 接受状态处理/回传。

提前顺序：保存本轮词表所需的logits和上轮草稿 → 原始主模型采样 → 原始接受状态处理/回传 → 本轮词表维护 → 草稿生成。输入准备所需的CPU接受数量有机会更早就绪；不预设能回收多少空隙。

`early_counts.py`在当前进程中移动框架原有的整个`async_state_update`块，保留GDN状态处理、stream/event依赖和align模式的接受数量语义。`dynamic_vocab.py`与上一版完全相同；为避免采样原地改写输入，提前顺序增加小型logits和上轮草稿快照，这部分开销计入端到端时间。

`run.py`先在两道自然结束题上比较输出token及每轮候选集合哈希，通过后各测32题自然结束、上限2048。候选集合记录只用于正确性预检，测速时关闭。另采两个128输出的PipeUtilization窗口，使用相同decode窗口定义比较空隙，排除prefill。采样耗时不作为无profiler吞吐。

`summarize.py`计算32题详细延迟与接受率；`analyze.py`、`prepare_input_breakdown.py`离线分析设备和Host；`export_evidence.py`核对源码、FP32状态、图捕获、Insight分组、SQL、服务器/本地复算后，仅导出过滤证据。原始请求、回答、token数组、seed、trace/DB和运行路径保留在私有数据区。

此前2卡首次模型加载OOM，未产生性能结果；第二次启动前检测到其他量化任务，未启动服务。用户随后授权改用6卡。不同卡的失败尝试不计入本次性能对照。
