# DFlash2 与 MTP：为什么本次只快约 9.6%

2026-10-20，在同一单张 Ascend 910B2、BF16、vLLM-Ascend 0.27.1rc1 独立环境，分别采集两条提示的 MTP 与 DFlash2，共四份 Level1 / PipeUtilization、CPU+NPU、带 shape 的 PyTorch Profiler 数据。主模型执行图开启，两组草稿均为 eager；MTP 为 1 候选，DFlash2 为 7 候选。这是对已有测试的分析，不是 SGLang 社区方案复现。

**结论：DFlash2 每次返回的 token 更多，但本次 eager 草稿流程也更贵，抵消了大部分收益。主要新增时间在主模型图之后的草稿与准备流程；候选路径选择本身并不是热点。**

## 先用无 profiler 请求解释 9.6%

下表由已有 SSE 返回时间重算，没有重跑基准。排除首个返回块后，严格满足 `token/s = 平均每次返回 token 数 ÷ 平均返回间隔`。这里称“返回块”，不把它自动等同于硬件图执行次数。

| 提示 | 方法 | 平均 token/返回块 | 平均返回间隔，两次测试 | 连续生成 token/s，两次测试 |
|---|---|---:|---|---|
| 矩阵乘解释 | MTP | 1.796 | 59.079 / 59.031 ms | 30.396 / 30.421 |
| 矩阵乘解释 | DFlash2 | 2.361 | 77.489 / 78.763 ms | 30.470 / 29.977 |
| HBM 解释 | MTP | 1.821 | 58.894 / 58.899 ms | 30.927 / 30.925 |
| HBM 解释 | DFlash2 | 2.898 | 77.177 / 78.833 ms | 37.546 / 36.758 |

第一条提示，DFlash2 每次多返回约 31.5% 的 token，但每次返回也多等约三成，收益基本抵消。第二条提示每次多返回约 59%，足以抵消等待，得到约 19%～21% 的收益。四次速度的中位数最终为 **30.673→33.614 token/s，+9.589%**。这是提示相关的结果，不是固定 9.6% 的算法上限。

## 新增耗时在哪里

以第一条提示为例，按硬件 `MODEL_EXECUTE` 边界划分每轮，以下是中位数；第二条提示的各项每轮时间接近。

| 采样中的每轮指标 | MTP | DFlash2 | 增加 |
|---|---:|---:|---:|
| 完整周期 | 65.320 ms | 92.433 ms | 27.113 ms |
| 主模型图时间窗口 | 48.845 ms | 52.965 ms | 4.120 ms |
| 主模型图结束至下一轮窗口 | 16.486 ms | 39.465 ms | 22.979 ms |
| 图外设备计算内核累计时间 | 6.726 ms | 12.091 ms | 5.364 ms |
| 周期内无计算任务时间 | 11.549 ms | 29.251 ms | 17.702 ms |

主模型从验证 2 个位置变为 8 个位置，每轮图窗口只增加约 4.1 ms。增加最多的是图后流程。通过原生 CPU 标签和 `async_npu` flow 关联设备任务，MTP 草稿约 **68 个设备内核/轮、2.95 ms/轮**；DFlash2 包含草稿与专用输出标签后约 **448 个/轮、8.01 ms/轮**。它有五层草稿模型，eager 执行需要更多小操作和下发。

CPU `draft_token` 包含时间为 **7.98→39.33 ms/轮**；这些时间包含等待且可能与设备执行重叠，不能再加到表中设备时间上。较长的设备计算空档与输入准备、slice/copy 等 CPU 工作重合，支持继续检查草稿图捕获与准备流程。但“无计算任务”还可能包括 DMA/控制/等待，不能将全部 17.7 ms 都叫 CPU 空转或可回收时间。

进一步分解：

- DFlash2 草稿五层的两组 FFN 合计约 **2.20 ms/轮**。
- 草稿 LM head + top-k 合计约 **2.02 ms/轮**，其中大词表矩阵乘约 **1.93 ms/轮**，top-k 的其余部分约 0.09 ms。不能把整个 2.02 ms 都归给 top-k。
- `selector_walk` 的设备内核仅约 **5.18 μs/轮**，不是本次主要瓶颈。
- 主模型 FFN 升维单次约 **287.156→310.780 μs**；48 层 GDN 的相关内核单次约 **25.658→49.448 μs**，是主模型验证窗口增加的一部分。
- `candidate_selector.forward` 的 Python 标签被编译消除，没有独立事件；没有将其零事件解释为零成本，也没有伪造独立测量。

## 采样开销与后续方向

带 shape 的采样使 DFlash2 请求约增加两成耗时，MTP 约增加一成。因此以上采样时间用于定位阶段，**正式提速仍以无 profiler 的 9.589% 为准**。不能把采样中 92.4 ms/轮直接当作正常运行的每轮延迟，也不能承诺全部空档都能被图模式消除。采样输出与既有正常请求的八项 EOS 前缀检查全部一致。

本次新 vLLM-Ascend V1 源码通过 `_use_aclgraph()` 与 `not speculative_config.enforce_eager` 控制草稿图，支持把合并草稿执行包装成 ACLGraph；我们的初次兼容配置显式给两组设置了 `enforce_eager=True`。这是一个有源码和时间线依据的后续方向，尚未完成该配置的无 profiler A/B 验证，不提前记为已提速。

## 公开成绩的分母

[作者模型卡](https://huggingface.co/incoai/Qwen3.8-27B-DFlash2#evaluation) 的 GSM8K 单并发成绩，AR 68.9、MTP 178.5、DFlash2 236.1 token/s。**3.43 倍的分母是 AR，DFlash2 相对 MTP 约快 32.27%**。该实验为 H200 / SGLang / FA3、两种方法均 7 候选、开启 xhigh 思考、随机采样，和本次初测条件不同。

[官方昇腾适配 PR](https://github.com/sgl-project/sglang/pull/35629) 另有 910C TP2、BF16、greedy、zero-shot GSM8K、2048 输出上限、关闭 RadixCache 的结果。该表中的 DFlash2 3.05 倍也相对无投机基线，不是相对 MTP。它还明确说明昇腾 selector 验证对随机采样会退回 greedy；本机源码核对仍保留该限制。
