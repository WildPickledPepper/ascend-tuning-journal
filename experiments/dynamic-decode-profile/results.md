后续离线追查已将图外空隙进一步缩小至输入准备与短草稿图的重叠关系，见[prepare input分析](prepare-input-analysis.md)。约96%的间隙位于草稿结束至下一主图启动之间；下面保留最初采样结论及逐步定位过程。

**主模型 FFN 仍是最大单项，约占 decode 的 34.5%；主模型其他线性投影约 16.1%。动态草稿词表把草稿投影本身降到了 0.37%，但选词、维护分数和整理候选新增了约 10.9% 的设备任务时间。另外约 13%～15% 未记录到计算任务，主要位于模型图之外。**

本轮只采集、分析，没有改算法、权重、NPU 内核、词表策略或默认配置。不能再沿用旧版“草稿大词表投影占18.6%”来描述当前动态4096版本。

**现在小head矩阵乘和权重gather都不是大头，候选集合的维护才是这一部分的大头。** Top8 kernel的Vector活动约96.90%、MTE2活动约5.83%；IndexFill的Vector活动约1.20%、MTE2约95.21%。两个热点的执行特征不同，不能统一说成大权重HBM搬运。

`AI_CPU`是设备侧AI CPU执行任务的分类，**不是主机CPU线程**。它说明这两个操作未走Cube/Vector的同类路径，但不能仅凭标签说主机CPU算不过来。

旧完整草稿词表采样每次大head约1.915ms，每轮七次约13.405ms；当前每次小head约42.05μs，每轮七次约0.294ms。路径确实大幅缩小；但当前每轮选词维护还要约8.540ms，以及图外准备、接受长度变化等成本。不同配置的旧采样只能帮助理解成本转移，不能把这些数直接相减当整网实测收益。

现有32题无profiler结果仍是完整→动态60.583→62.736token/s（+3.55%），见[原报告](../gdn-fp32-gsm32/results.md)。本轮profile不替代该结果，也没有证明上述某一项单独解释全部收益。

## 图外的空隙需要单独查

首题无计算区间304.391ms，其中模型图内仅9.921ms，**图外294.470ms**。另一题为685.208ms，其中图内21.652ms、图外663.556ms。图内计算衔接较紧，空隙主要位于图外流程。

按前后设备任务名字定位，首题最大的三组边界是：

- `Sub → Sub`：98.095ms；
- `Fill → Sub`：82.718ms；
- `Sub → Arange`：36.772ms。

三个边界累计217.585ms，占整个decode约10.25%。这些数是**相邻kernel之间的空隙**，不等于Sub、Fill或Arange自身执行这么久，也不是可直接消除的收益。

时间线可见Event同步；它会覆盖设备正在执行的时间，不能将其CPU墙钟加到设备时间上。新增`dynamic_vocab.update/repack`标签同样是异步CPU scope，其1.600/0.757ms均值不能代替设备侧8.540ms/轮的任务总量。

现阶段可定位到模型图之外的零散张量操作与同步边界这一层，下一步需要沿调用链确认它们在输入准备、状态/元数据更新或后处理中的具体归属。**还没有把所有图外空隙唯一归因于Python下发、设备等待、DMA或profiler开销。** Level1及record_shapes也会扰动大量eager操作；没有当前同配置开/关profiler的配对实验，因此不能宣称生产运行中有14%的主机空等。没有为此擅自重跑性能基线。

因此空隙增长不只是分母变化。通过`torch_to_npu`的flow关联到CPU阶段，当前约92.2%的空隙，其后续kernel的Host调用属于`prepare input`；草稿图下发相关空隙约1.495ms、动态更新相关约0.294ms，不能把整个14.35%直接说成动态TopK任务的执行时间。输入准备负责下一轮输入及位置/缓存等参数的整理，已经成为进一步定位的具体调用链。

关联说明“下一项任务由哪段代码下发”，不能单凭它区分输入准备自身变慢、同步依赖、此前被较长草稿图遮住的开销、线程调度及profiler扰动。两版`prepare input`的CPU墙钟均值29.510→38.925ms，含异步与等待，不可直接当可优化CPU计算时间相加。本轮没有新增上机验证，也没有改代码解决它。

另澄清词表表格：2.85%是**主模型与草稿投影合计**，即`(52.454+7.947)/2121.816≈2.847%`。主模型仍投影到完整248320词表，单轮耗时基本相同；变化的是草稿七次投影13.405→0.294ms/轮。主模型占比2.69%→2.47%来自不同的整段decode分母，不能理解为主模型词表也被缩小。

1. **主模型FFN供数链**：仍占三分之一，保持现有packed/预取，不因比例变化误判已解决。
2. **动态词表TopK和IndexFill**：是当前已经实测到的设备热点，先看现有操作语义、实际执行路径及是否有不必要重复；任何替代实现须另行授权、校验接受长度与端到端吞吐。
3. **图外准备、后处理与同步**：先按调用链细分上述大空隙，并核对采集扰动；不能盲目重写Sub等小kernel，也不能把gather当主要瓶颈。

这只是定位顺序，不是已经实施的优化。当前结果不外推到多并发、长上下文或其他接受率。

## SQL口径

Compute CTE保持技能原样。主查询为聚合TOP20；完整SQL及各采样whole/decode结果保存在上述数字证据中。时间为ns，报告转为ms。

```sql
WITH compute_view AS (
    SELECT c.globalTaskId, ROUND(t.endNs - t.startNs) AS duration_ns, n.value AS op_name, type_str.value AS op_type
    FROM COMPUTE_TASK_INFO c
    LEFT JOIN TASK t ON t.globalTaskId = c.globalTaskId
    LEFT JOIN STRING_IDS n ON n.id = c.name
    LEFT JOIN STRING_IDS type_str ON type_str.id = c.opType
)
SELECT op_name, op_type, COUNT(*) AS calls, SUM(duration_ns) AS total_ns
FROM (SELECT * FROM compute_view LIMIT -1)
WHERE globalTaskId IN (SELECT globalTaskId FROM TASK WHERE startNs >= ?)
GROUP BY op_name, op_type ORDER BY total_ns DESC LIMIT 20;
```

内层`LIMIT -1`是避免SQLite选择二次方TASK扫描的优化屏障，不改变CTE和最终TOP20结果。参数是首个主模型图开始的真实时间戳，留在原始私有产物中。
