# 已有整网 profiling：FFN 优化前后同口径比较

**FFN 绝对耗时和占比都下降了。** 最近的已有对照是“已做 down 预取、尚未 gate/up 重排”：主模型 FFN 在相同 26 轮里从 **758.812 ms 降到 684.598 ms，减少 9.78%**；占整个 decode 从 **38.98% 降到 36.50%，下降 2.48 个百分点**。

这是 2026-10-22 的离线复算，只读取已有文件，新增 NPU 请求为 0；没有 SSH 启动服务、重新采集、改内核或重跑基线。[复算代码](compare_history.py)、[完整过滤证据](../../evidence/2026-10-22/ffn-profile-history-comparison.json)。

## 比较条件与限制

三个版本均为同一 Qwen3.8-27B、BF16、TP1、单并发、MTP7、主/草稿图 capture8，输入同一 GSM8K 首题，模板后 121 token，输出 128 token 且逐 token 完全一致。各含 26 个主模型图、26 个草稿图；每轮主模型 gate/up、SwiGlu、down 各 64 次，草稿各 7 次。

统一窗口：首个主模型 `MODEL_EXECUTE` 到最后计算任务结束。排除之前的 prompt/eager 工作，包含主模型验证、草稿、词表投影与后处理。主模型 FFN 统一包括 gate/up 矩阵乘、SwiGlu、down 矩阵乘；按时间并集统计，不把 CPU scope 或流水活动时间相加。自定义 kernel 用图边界归属，不用哨兵 Model ID。每个版本的分母都是其完整 decode 窗口，统计定义相同，不强行把总时长设成同一个值。

**旧两份在物理 6 卡、2026-10-21 采集；当前版本在物理 7 卡、2026-10-22 采集。** 因此下面是相同工作量、相同统计口径的历史观测差值，不是同卡同日严格 A/B，也不能将全部差值唯一归因于权重重排。三者均为 Level1/PipeUtilization/record_shapes，但 op_attr 等跟踪配置有差异。最近一次 7 卡 packed-control 端到端测试没有整网 profiling，不能凭空补出该版本的 kernel 时间。

## 主模型 FFN 确实变快、占比确实下降

| 已有版本 | 主模型 FFN，26轮累计 | FFN，每轮 | 整个 decode 窗口 | FFN/decode |
|---|---:|---:|---:|---:|
| 本轮原生 FFN：未 down 预取、未 gate/up 重排 | 771.514 ms | 29.674 ms | 1964.282 ms | 39.277% |
| 已做 down 预取，尚未 gate/up 重排 | 758.812 ms | 29.185 ms | 1946.773 ms | 38.978% |
| 当前：down 预取＋gate/up 重排＋prefill 直读 | 684.598 ms | 26.331 ms | 1875.480 ms | 36.503% |

从最近的“已 down 预取”版本到当前：

- 主模型 FFN 减少 **74.214 ms，即 9.780%**；每轮减少约 **2.854 ms**。
- FFN 占比减少 **2.475 个百分点**，38.978%→36.503%。
- 整个 decode 设备窗口减少 71.293 ms，即 3.662%；其余任务合计略有增加。不能把该设备窗口降幅当作新测的无 profiler E2E 或 token/s。

从表中最早的原生 FFN 到当前，主模型 FFN 减少 **86.916 ms，即 11.266%**；占比 39.277%→36.503%，减少 **2.775 个百分点**。此前“仍然 36.5%”只能表示优化后还有这么大，不能理解成优化前后都为 36.5%；当前数据明确显示占比下降。

如果只以各自的主模型图窗口为分母，FFN 占比分别为 **56.574%→56.262%→53.557%**。这组数不能和“占整个 decode”的 39%/36% 混用。

## 下降主要来自 gate/up

以下都是完整模型 profiling 中的实际 kernel，三者主模型每项均为 1664 次，不是之前独立微基准的 279→239 μs。

| 主模型路径 | 原生 FFN，平均每次 | 已 down 预取，平均每次 | 当前，平均每次 | 已 down 预取→当前 |
|---|---:|---:|---:|---:|
| gate/up | 298.185 μs | 297.990 μs | 254.834 μs | **−14.483%** |
| down | 154.047 μs | 146.222 μs | 145.848 μs | −0.256% |
| SwiGlu | 11.418 μs | 11.804 μs | 10.735 μs | −9.057% |

“已 down 预取→当前”主模型 FFN 共节约 74.214 ms，其中 gate/up 节约 **71.812 ms**。down 约持平；激活的 1.779 ms 差异也被如实列出，但它没有被本次直接改写，不能认定为重排的独立收益。

down 自身近乎不变，而 gate/up 明显变快、decode 分母缩短，所以 down 占比反而从 **12.498% 升到 12.940%**；这不代表 down 变慢。总 FFN 占比仍下降，因为 gate/up 的下降更大。

## 搬运流水活动与任务耗时要分开

gate/up 的 MTE2 平均活动时间从原生 **281.732 μs**、已 down 预取 **281.637 μs**，降到当前 **246.291 μs**；这与其 kernel 耗时下降方向一致。

down 从原生到当前，kernel 154.047→145.848 μs，但 MTE2 平均活动时间 **129.152→135.053 μs**，并没有降低。前视预取改善的是各流水的重叠与等待，不能笼统说“预取把 MTE2 活动时间降低了”。各流水可能并行，也不能把活动时间的差值直接解释成总时长中回收的等待。

因此用户提出的判断在当前数据中成立：**主模型 FFN 加速后，其占整个 decode 的比例确实降低，最近阶段下降约 2.5 个百分点。**

## 校验与资料归档

- 三份采样正常 Stop，trace/CSV/DB齐全，统一取相同 26 轮；同输入、同输出 token 已核对。
- 旧两份各 193 组、当前 195 组，**581 个 Insight 分组**的次数/累计耗时与 CSV 逐项一致。
- 每份 decode TOP20 用 DB skill 原样 Compute CTE、只读 SQLite 验证；没有 msprof SQL MCP 可用，不声称通过该工具执行。
- 当前版本按本次统一算法得到的全部互斥类别和 decode 窗口，与上一轮已发布分析完全一致。
- 过滤证据保存 CSV、task CSV、profiler_info、Insight 回应及复算脚本 SHA256；原始请求、私有路径和全量 trace/DB不入库。

这次完成的是统计口径对齐与历史复算，未执行任何新性能实验。跨卡、跨日期的限制保留，不为补齐严格 A/B 而重新启动服务。
