# 优化后的 decode 主要耗在哪里

后续补充：[已有三份采样的FFN同口径对照](history-comparison.md)。主模型FFN占比由原生39.28%、已down预取38.98%，降到当前36.50%；FFN绝对耗时确实降低。旧6卡/当前7卡，跨卡跨日观测，不作为单项改动的严格同卡归因。

**当前单卡、单并发、MTP7 场景，主要耗时仍在设备上的小批量矩阵乘和权重供给。主模型 FFN 最大；草稿反复执行的大词表投影是另一个明显大头。没有发现 CPU 下发让设备长时间空等的现象。**

这是对已优化版本的新采集：保留 BF16、gate/up 权重重排、M8 down 预取和 prefill 直接读取。本轮只加采集入口与离线分析，没有改变推理内核、权重表示、MTP 参数或共享框架源码，没有部署为默认版本。

## 测了什么

| 条件 | 本次设置 |
|---|---|
| 硬件 | 物理 7 号 Ascend 910B2，单卡 TP1 |
| 模型 | Qwen3.8-27B，BF16，64 层 dense FFN |
| 调度 | 并发 1，MTP7，主/草稿均图回放，capture size 8 |
| 其他参数 | 上下文 4096，batch token 上限 512，预算 0.97，关闭 prefix cache，SSM/cache BF16 |
| 输入/输出 | GSM8K 第一题，模板后输入 121 token，固定输出 128 token；三个指标组相同请求 |
| 采样 | Level1、CPU/NPU、record_shapes、Text/DB；分别 PipeUtilization、L2Cache、Memory |
| 预热 | 排除 65-token 输入/64 输出、首题 512 输出；另一次无 profiler 的 128 输出用于输出与采集开销核对 |
| 时间 | 2026-10-22 北京时间约 09:21–09:22 采集；09:22:50 服务退出，09:27:17 再次确认 7 卡无进程、8047 关闭 |

三个采样各含 26 个主模型图和 26 个草稿图，三个 128-token 输出均与无 profiler 参考逐 token 一致。64 层 65-token 真实输入检查通过；计时采集窗口 192 次 prefill 直接读取，解包回退 0 次。M8 的 Python 计数在图回放期间不增长，不能当设备调用次数。

设备存在 `81078603` 通信端口链路 up→down 告警，HBM ECC 计数为 0。没有调整硬件；本次 TP1、不使用卡间通信，采样未发现 HCCL kernel。告警保留在释放回执，不据此宣称设备完全无告警。

## 整个 decode 的耗时分摊

下表以 PipeUtilization 的 **1875.480 ms 设备窗口**为分母：首个主模型 `MODEL_EXECUTE` 到最后计算任务结束。排除之前的 prompt/eager 工作，包含主模型验证、草稿生成、词表投影与后处理。它与客户端“收到首 token→收到末 token”的边界不同，不直接相减或换算成新的 token/s。

| 部分 | 累计互斥时间，ms | decode 窗口占比 |
|---|---:|---:|
| 主模型 FFN：gate/up | 424.044 | 22.61% |
| 主模型 FFN：down | 242.692 | 12.94% |
| 主模型 FFN：激活 | 17.863 | 0.95% |
| 草稿 FFN：gate/up、down、激活 | 80.470 | 4.29% |
| 词表投影：主模型与草稿 | 399.073 | 21.28% |
| 主模型其他线性投影 | 328.219 | 17.50% |
| 草稿其他线性投影 | 49.320 | 2.63% |
| Attention 核心任务 | 77.192 | 4.12% |
| 其余计算任务 | 239.308 | 12.76% |
| 无计算任务的间隙 | 17.300 | 0.92% |

**主模型 FFN 合计 36.50%；加上草稿 FFN，总计 40.79%。** “Attention 核心任务”不含前后的线性投影，也不含所有 GDN 门控、卷积与布局整理；其余任务包括这些操作，以及归一化、Slice、Transpose、Concat、采样等。不能据 4.12% 说整个 Attention 模块只占 4.12%。

主图窗口每轮约 49.164 ms，草稿图每轮约 19.834 ms，整个设备窗口平均每轮约 72.13 ms。前两者只是设备图窗口，不能把 CPU scope 的墙钟再加上去。

L2Cache、Memory 两组 decode 窗口分别为 1875.550、1874.636 ms；主要类别占比一致。三组是不同硬件指标采样，不是多轮无 profiler 性能分布，也不声称获得新的吞吐提升。

## 为何判断主要受权重供给限制

下面的活动比例按任务持续时间加权；指标来自不同请求，按相同路径分组对齐。

| 路径 | 单次 kernel 均值，μs | MTE2 活动 | MAC 活动 | L2 读命中率 |
|---|---:|---:|---:|---:|
| 主模型 packed gate/up | 254.834 | 99.25% | 12.82% | 0.530% |
| 主模型 down 预取 | 145.848 | 98.47% | 16.71% | 6.711% |
| 词表投影 | 1918.621 | 99.59% | 11.69% | 0.0193% |
| 主模型其他线性投影 | 71.726 | 94.39% | 12.49% | 2.745% |

其含义是：这些任务执行期间，供数流水几乎一直活动，乘加活动相对少；大量读取没有被 L2 缓存承接。结合 M8 或 M1 的小行数、大权重矩阵，证据支持权重供给限制，而非 Cube 算术吞吐不足。

**MTE2 活动 99% 不等于 HBM 带宽达到峰值的 99%。** 同样不能把 kernel 耗时全称作 HBM 读取时间：内部还包含 L1/L0 搬运、同步、乘加和写回。当前结果能够定位到供数链，不能唯一判定究竟是 HBM 控制器、访问组织、L2→L1 或核内流水中的哪一个物理上限。

Memory 指标组已保留原始 `aic_*_bw(GB/s)` 字段，但没有把它外推为整卡 HBM 实际总带宽。该版本字段的 PMU 事件、块数、频率和归一化口径尚未完成系统级校准；本轮没有同时采集整卡 HBM 总线计数，不提供新的 HBM TB/s 或实际 HBM 字节数结论。

## 词表投影为何值得单独研究

词表投影把隐藏向量变成各词的分数。当前矩阵为 `248320×5120`，BF16 权重约 **2.543 GB**。

| 位置 | 次数 | 累计 kernel 时间 | 整个 decode 占比 |
|---|---:|---:|---:|
| 主模型验证后的投影，M8 | 26 | 50.533 ms | 2.69% |
| 草稿生成中的投影，M1 | 182＝26×7 | 348.540 ms | 18.58% |

草稿的七次投影约占草稿图窗口的 **67.59%**。每轮主模型一次加草稿七次，共八次使用这张大矩阵；按矩阵大小相加是约 20.342 GB 的逻辑权重读取量，**不是实测 HBM 总线流量**。L2 命中率很低，说明当前未获得足以消除该成本的缓存复用。

这也解释了为什么只盯住 64 层 FFN 不够：草稿主体只有少量层，但输出词表仍很大，反复投影可以单独占掉近五分之一的 decode。

## CPU、通信和采集开销

本次 decode 的无计算间隙仅 0.89%–0.92%，Pipe 组最大单个空隙约 204 μs。空隙还可能包含 DMA、同步或其他硬件任务，因此不能全部归咎于 CPU。相反，CPU 侧较长的同步 API 通常包含等待设备执行，不能据其累计耗时认定 host bound。

采样配置下无 HCCL kernel；单卡 TP1，没有发现卡间通信瓶颈。数据搬运仍发生在算子内部，通信占比为零不代表没有权重搬运。

同请求无 profiler E2E 2.146 s、TTFT 354.235 ms；三个采样 E2E 2.360–2.386 s、TTFT 557–583 ms。采集尤其增加了 prefill/主机跟踪开销。这里保留这些数值只说明干扰边界，不能与上一轮正常测速混成新的性能成绩。decode 的三组设备分摊相近，也不代表 profiler 绝无干扰。

## 数据校验与结论边界

- 三组均正常 Stop，`profiler_info` 有结束信息，Text/DB、trace、kernel CSV 完整。框架有“RECORD 状态停止”的 schedule 提示；已核对最终结束元数据、26+26 图、固定 token 输出及解析产物后采用，没有把该提示忽略为精度或性能结论。
- 自定义 kernel 的 `Model ID=4294967295` 是缺省值，不能作为主图 ID。按原生 attention 投影确定主/草稿身份，再按 52 个 `MODEL_EXECUTE` 和原生图尾重建时间归属。每主图断言 64 个 packed gate/up、64 个 down；每草稿图 7 个 down；确认 decode 内没有 `packed_prefill`。
- 编译版 Insight `operator/statistic` 的全部 195 个组与 CSV 次数/累计时间一致。使用 DB skill 原样 Compute CTE，通过只读 SQLite 验证整份采样及 decode TOP20；本会话无 msprof SQL MCP，不声称使用该工具。服务器和本地复算 JSON 完全相同。
- 原始归档 SHA256：`df98e0e26b319ae5b7c3535b8d80e1bcbdbf716ec275c3355270cabcde240745`。原始 trace/DB 与私有运行路径保留在外部数据区。
- 仅一个短输入、并发 1、MTP7 的场景；不外推到长上下文、其他接受率或大 batch。当前实验版本既有的大 M BF16 舍入边界仍然存在，本轮 token 一致不等于所有 shape 的逐位证明。

定位后的优先级是：先评估主模型 FFN 的供数效率，以及 MTP 草稿反复做词表投影的成本，再看 attention 周围的线性投影。仅消除当前记录中的无计算空隙，理想可回收时间也不足 1%；这不是进一步优化下发能获得大量收益的证据。本轮到此结束，保持 7 卡释放，不自动修改或部署新方案。
