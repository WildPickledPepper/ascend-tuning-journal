# 单张 910B2：BF16、七候选 MTP 与草稿图

用户要求检查能否在单卡上达到此前双卡约70 token/s。2026-10-20仅使用物理卡6，保留卡7原服务，完成同四道GSM8K测试。

**本轮单卡跑通，四题端到端吞吐42.167 token/s，未达到此前双卡69.748；长回答第三题为53.254 token/s。** 四题均正确且自然结束。这里只证明本配置的实测结果，不声称单卡上限为42或53。

## 配置与显存依据

沿用此前固定的SGLang合入版本`30d0eb2ca9dfcfcfcec5eb86c2bb5a83132a766d`及官方NPU `2026.9.1`包，私有CANN9.1、torch2.10 / torch_npu2.10.post4。主模型、内置MTP与SSM状态均BF16，没有量化、没有自写NPU内核。

| 项目 | 本次单卡 | 此前双卡 |
|---|---|---|
| 并行 | 物理6，TP1 | 物理6、7，TP2 |
| MTP | EAGLE，steps7、topk1、验证窗口8 | 相同 |
| 图 | 验证图、草稿decode与extend图均捕获成功 | 相同三类图均捕获成功 |
| 最大并发 / 前缀缓存 | 1 / RadixCache关闭 | 相同 |
| 上下文 / 缓存token上限 | 4096 / 显式8192 | 32768 / 框架自动分配 |

| 请求 | 同四题、同payload、T0/top_p1/top_k1、max2048 | 相同 |

原90%预算启动被框架内存检查拒绝，没有性能结果。实际加载主模型约51.01 GiB，草稿临时再占5.53 GiB，剩余约3.97 GiB；报错仅按已加载权重给出的最低静态比例约93.44%，还不能覆盖后续状态与KV缓存。

按本机分配公式核对，除已加载权重外还需约1.32 GiB的SSM/卷积状态与中间缓冲、0.10 GiB的多模态预留，以及8192 token主模型KV约0.50 GiB和草稿KV约0.03 GiB。因此改为97%预算并保留8192 token硬上限，避免无依据逐个试比例。预算参数不等于实际占用，也不是提速开关；框架后续会共享主模型和MTP的embedding/lm_head并释放重复权重。

日志确认主模型KV为8192 token，K/V各0.25 GiB；草稿K/V各约0.02 GiB。三类图完成后框架报告可用约5.21 GiB。服务就绪时两个本实验NPU进程合计57238 MiB，即**55.90 GiB**；这是快照，不是持续采样峰值。

降低上下文上限没有截断这四题：每题prompt token数加请求的2048输出上限均小于4096；实际均以`stop`自然结束。内存配置仍与TP2不同，不伪称所有运行条件完全相同。

## 为什么这次单卡能到40～50区间

旧单卡vLLM配置只起草一个候选、草稿显式eager。旧累计计数每轮约1.840 token；正式流式回执每返回块约1.8 token、相邻块约59ms，对应约30 token/s。

本次仍为一张910B2与BF16，但用七候选、草稿图及SGLang执行路径。日志窗口每轮产出3.95～5.35 token，候选接受率42%～62%。一次主模型验证可以带出更多token，把大模型权重读取成本分摊到更多输出上；草稿图减少逐条下发操作的开销。这解释了配置的优化方向，但候选数、框架、草稿执行模式和题目同时变化，没有逐项A/B，不分配各项收益百分比，也不将旧连续生成30与新端到端42直接写成严格的同条件提速。

本次连续生成日志中间三个窗口分别48.21、51.73、48.53 token/s，最后一个窗口63.91；首个窗口仅1.23且含请求边界/此前空闲，不当作最低解码性能。最后一个窗口也不当作稳定64的保证。首题耗时6.052秒偏长，尚未用profiler定位其内部耗时，不猜测为冷编译或某一算子。

`/server_info`返回`avg_spec_accept_length=4.575`，但源码`scheduler_components/metrics_reporter.py`显示累计计数仅在日志窗口上报时归并，还可能混入预热并遗漏未上报尾段；因此不将其称为四题精确平均接受长度或接受率。保留该字段与窗口原始摘要供复核。

本轮没有新增msprof/Insight采样，所以不把剩余差额进一步归因于某个内核、HBM峰值或主机瓶颈。当前明确结论是：单卡BF16 MTP7和草稿图可以部署，已观察到40～50区间，但这轮没有达到双卡约70。
