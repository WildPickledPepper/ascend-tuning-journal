# 下一包权重提前搬运：算子与完整27B验证

本次实现通过所测正确性检查，独立算子延迟下降6.11%，模型内目标算子下降5.33%；同四题完整27B吞吐中位数59.386→59.774 token/s，约+0.653%。这是小收益，尚不能外推为不同题目、运行批次均有稳定提升。没有修改默认安装或保留常驻服务。

## 1. 算子与实验条件

用户在原生预取审计后明确要求：把降维下一包权重提前搬，保持BF16及原来的累加顺序，先验证算子、再测完整模型。本次是独立编译的M8专用内核，原生CANN不被覆盖。实现与依赖见[代码说明](README.md)，数值来自[过滤证据](../../evidence/2026-10-21/down-m8-prefetch.json)。

固定形状为 `[8,17408] × [5120,17408]ᵀ`；23核、每核N112×2（最后一组N80）、K512×34，每包8次K64 MMAD。保留原生每核的K绕行/反向遍历及包内累加顺序、FP32累加后BF16输出。L1仍为256KiB双缓冲，不减少权重字节、不量化、不预转全局权重NZ。

新代码有两个版本：mode0按包搬完再计算；mode1计算当前包前，将下一包下发到已释放的另一个L1槽。两者共用分块、计算和同步实现，用于隔离本实现的预取增量。与原生相比，标量/L0调度也不同，不能将全部差额都算作预取收益。

单卡910B2；完整模型为Qwen3.8-27B，vLLM0.27.1/vLLM-Ascend0.27.1rc1、torch2.10/torch_npu2.10、CANN9.1。TP1、BF16、MTP7、主/草稿图模式capture8、maxlen4096、maxseq1、prefix cache关闭；同四道GSM8K、greedy、输出上限2048。使用公开SGLang评测脚本，运行服务仍是vLLM。正式测速无profiler，另取首题128token采样。

## 3. 为什么整模型只快一点

目标降维原本只占本次完整采样窗口的12.178%。这部分减少5.330%，等于总窗口约0.649%；四题无profiler吞吐增加0.653%，量级相符。这是用实际占比解释收益，而非从“有双缓冲”推测提速。

采样窗口实际减少22.286ms，其中目标算子节约15.197ms，其余合计减少7.089ms。只有各一份采样，不能把其余变化全部归因于预取，也不能把采样窗口降幅直接当作四题吞吐收益。

| 新版本剩余部分 | 占新版本采样窗口 |
|---|---:|
| 升维FFN | 23.619% |
| 其他矩阵乘 | 18.743% |
| 词表投影 | 17.832% |
| 其他计算 | 15.952% |
| 无compute区间 | 12.215% |
| 本次目标降维 | 11.639% |

无compute区间可能含下发、非计算任务和同步，不能全称CPU空转。

本次没有让HBM读取字节减少，MTE2活动时间反而更长，因此**不能宣称HBM→L2带宽已提升或MTE2自身耗时已缩短**。mode0/1对照支持：提前下发下一包在本实现中有小收益。原生→新版本还包含标量/L0实现变化，Scalar活动大降也不能直接当作消除76μs关键路径等待；各流水活动互相重叠，不可求和。

## 4. 正确性、失败与采用判断

24个输入种子、4档输入尺度、mode0/1共1,966,080个输出比较全部有限且与原生逐位一致；4个案例的两个模式通过图回放和更新输入检查，4组不同权重图回放结果也一致。完整模型两版本三轮四题的所有token ID、消息和结束原因相同，128token采样请求输出也一致。验证覆盖这些样本，不宣称任意输入的形式化等价。

早期两版出现L0A读写冲突，随后补齐逐MMAD消费完成依赖，重新验证通过；失败轮未纳入性能。CPU仿真超时，仅176/544条MMAD、缺END且bin导入失败，该产物不用于完整流水或上板WAIT结论。910B2没有在本次取得真实逐条WAIT时间；本次收益依据真实上板算子与完整模型测量。

判断：保留这一**可回退实验实现**，不设为默认。前视确有小的局部收益，但仅改占比约12%的降维，不能期望整模型大幅提升；也没有证明HBM供数链被根本解决。不再追加相同基线，不自动扩大内核重写范围。
