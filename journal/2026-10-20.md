# 2026-10-20｜NZ 跨层读取退化：实采 TLB 与 HBM

时间使用 Asia/Shanghai；下面的采集区间依据同一服务器的采集 receipt UTC 转换，恢复检查依据进程检查记录，没有用文件修改时间补造。

### 09:12—09:18｜采到 SMMU/TLB、L2 与 HBM，并做权重复用顺序对照

- **用户要求**：继续查为什么跨 64 层读不同权重变慢，争取采到 TLB 或内存控制器计数，用 ms 工具定位具体原因，不能靠猜。
- **保持条件**：物理 6 单卡、BF16、原 CANN 矩阵乘；7 号卡基线保留。临时服务仅增加主机观察 extension 和隔离 RPC，没有重写或编译 NPU 内核，没有更改共享 CANN、驱动或全局大页配置；没有重复整模型 8 请求基准。
- **采集方法**：检查本机 msprof 与安装源码，确认 `--l2=on` 包含 SMMU 事件。先启动 PyTorch Profiler 的 `l2_cache=True`，再捕获新图并回放 6 次；PipeUtilization 和 L2Cache 分开采集。稳定统计排除前两次回放。系统 HBM 采样仅选择物理 6、100 Hz，阶段绝对时间对齐，前后裁掉 100 ms。
- **控制变量**：small/full 都是 128 次原生矩阵乘，权重逻辑读取量均 34225520640 B；区别是两层循环工作集 1069547520 B 与 64 层不同权重 34225520640 B。同层 X/W/Y 地址、shape、stride 保持一致。
- **直接计数**：升维每调用 TLB 请求数均约 697601，但 miss **33.47→3926.23**，耗时 **236.044→293.089 μs**；降维请求数约 354734，miss **734.80→1967.39**，耗时 **137.592→165.820 μs**。MAC 时间近似不变，主要增加的是 MTE2。TLB miss 百分比不是等待时间百分比。
- **L2 数据缓存对照**：small/full 升维读命中均约 **0.1293%**，降维均约 **1.7329%**。这次退化不能用 L2 权重数据更冷解释。
- **复用顺序干预**：sweep2 与 adjacent 都读取相同 64 层权重、256 次矩阵乘；仅将同一权重的两次调用从隔完整网络改为紧邻。相邻升维第一次→第二次，miss **3926.13→176.84**，耗时 **293.326→241.558 μs**，MTE2 **270.173→227.825 μs**，L2 数据读命中只从约 **0.1293%→0.1547%**。这支持主要原因是地址翻译复用，而非只观察相关性。
- **降维对照的边界**：立即重读的降维权重 170 MiB 小于本机平台配置的 L2 192 MiB，第二次数据命中接近 100%；不能把其全部收益归给 TLB。升维权重 340 MiB、第二次 L2 命中仍极低，是更干净的翻译复用对照。无 profiler 的隔离图中，sweep2/adjacent 中位数 **229.269/199.997 μs/次**；不能据此直接重排真实网络或宣称整模型提速。
- **HBM 实测**：完整覆盖的四阶段 small/full/small/full 总读带宽分别 **1.436916/1.166834/1.435562/1.166691 TB/s**；四个 HBM 访问统计单元负载最大相对差异小于 0.02%，HBM 时钟始终 1600 MHz。这里没有取得每 bank 队列、行冲突或控制器等待周期计数，不把这些未测字段写成已经排除。
- **结论**：跨层大工作集拉长映射复用间隔，SMMU/TLB miss 增多，是本次复现的 NZ 权重搬运退化的主要原因。不是矩阵乘算术量增加，也不是已观察到的 HBM 降频。没有每次 miss 的 stall-cycle，不能逐微秒分摊；此前完整模型升维额外约 12.3 μs 的残差仍未全部解释。
- **失败与修正**：PyTorch 解析未保留中间 soc_pmu.db，后来从非空 `socpmu.data` 与官方 CSV 取到计数；首次 18 秒系统采样未覆盖最后一阶段，时间覆盖断言识别后，仅使用后续完整 36 秒采样做四阶段比较。全局 HA 的 L2 Hit Rate 为 N/A，改用独立 AI Core L2Cache PMU；未把未配置的 QoS 字段当作等待计数。
- **结构化验证**：按安装源码解析 80 B SMMU 记录，逐记录 `hit+miss=request`，逐 stream/task 与官方 miss 比例校验至导出精度。编译版 Insight 后端的 8 份采样、16 项形状统计，其次数和全 6 次均值均与 CSV 对齐；稳定 4 次口径单列。TLB 来自 msprof 原始记录与 CSV，未伪称 Insight operator API 本身含该字段。
- **产物**：[完整报告及复现脚本](../experiments/nz-hardware/README.md)、[过滤计数与后端核对](../evidence/2026-10-20/nz-hardware-comparison.json)、[来源哈希](../evidence/2026-10-20/nz-hardware-source-manifest.json)。原始 DB、trace、PMU 二进制、权重和服务器路径保留在私有环境。

### 09:54—10:30｜在单张 910B2 上用 vLLM 验证 BF16 DFlash2，与同版本 MTP 对照

- **用户要求**：检查 DFlash2 能否在 910B2 使用，保持 BF16，显存允许则试跑并与内置 MTP 对比；用户明确询问 vLLM 能否使用，以及 95% 预算的实际显存占用。
- **软件核对**：原 0.26.0 环境缺少 DFlash2 注册。服务器已有官方 vLLM-Ascend 0.27.1rc1 镜像，其中包含 `DFlash2DraftModel` 和 proposer。镜像的框架源码提取到独立目录，以独立 venv 复用原正常工作的私有 CANN 9.1.0、torch 2.10.0 / torch_npu 2.10.0.post4；两个框架 checkout 无修改。没有覆盖原环境、全局 pip、共享驱动或 CANN，没有重写 NPU 内核。
- **权重**：09:54:23—09:55:20 下载固定版本草稿并通过官方 SHA256 校验；5 层、1,924,404,480 参数、81 个 BF16 tensor，文件 3,848,817,896 B。文件字节数不等于运行时总显存。
- **启动问题及修正**：09:57 和 10:02 的普通容器路线先遇到无用户名映射、后遇到设备数量为 0，均在模型加载前退出；没有使用 privileged 或开放其他卡。转为原生独立环境后设备识别正常。10:07 初版前端注册包装器缺少 `__main__`，spawn 子进程递归启动，已修正。各次失败均恢复原 MTP 并保存回执，没有产生可用测速结果。
- **显存依据**：10:12 轮次使用原 90% 预算，BF16 主模型和草稿加载阶段消耗约 **53.9677 GiB**，但缓存可用仅 **0.77 GiB**，4096 上下文需要 **3.54 GiB**，因此框架拒绝启动。按已测缺口把两组预算同改为 95%；DFlash2 可用缓存变为 **3.82 GiB**，主模型图约 **0.56 GiB**，成功完成推理。10:23:16 服务就绪时 NPU 进程 **60,046 MiB ≈ 58.64 GiB**；MTP 对照 10:29:39 就绪时 **59,942 MiB ≈ 58.54 GiB**。这是进程就绪快照，不是持续采样的峰值。95% 是框架预算比例，不能直接将标称 64 GiB×95% 当成该进程实占。
- **公平对照**：两组均为物理 6 单卡、BF16、TP=1、单并发，主模型 `FULL_DECODE_ONLY`、草稿 eager，上下文上限 4096、调度 token 上限 512、无前缀缓存、无 profiler。DFlash2 为 7 候选，MTP 为 1 候选；固定两条中文提示各两次、每次 256 token，先预热再计时，另做三条输出检查。7 号卡基线保留；没有使用它分担草稿。
- **正式结果**：DFlash2 于 **10:24:28**、MTP 于 **10:30:38** 完成。连续生成中位数 **30.6727→33.6140 token/s（+9.589%）**；首 token **282→372 ms**，请求总耗时中位数 **8.596→8.023 s**。矩阵乘解释提示 **+0.24% / −1.46%**，HBM 解释提示 **+21.40% / +18.86%**，收益并不一致。历史 0.26.0 的 31.136 token/s 使用不同输出长度，未拿来直接归因新方案。
- **投机计数**：含预热、4 次性能请求、3 次输出检查，MTP 750 轮、750 候选、接受 630；DFlash2 498 轮、3486 候选、接受 885。候选接受率 **84.00% / 25.39%**，按 `1+accepted/drafts` 为 **1.840 / 2.777 token/轮**。这能证明候选确实进入验证流程；不能将接受率当成精度分数，也没有用该统计单独推算实际加速比。
- **输出边界**：7 项原始完整 token ID 比较 **5 项相同、2 项不同**；不同项在正常回答结束后：首次 EOS 零基索引 246、首次差异 253，源于固定长度测速设置 `ignore_eos=True` 的后续续写。按目标 `generation_config.json` 的 EOS ID 截到首次结束符或输出长度上限，**7 项前缀全部一致**。计算、代码检查最长 96 token，不宣称回答完整；本次不构成广泛精度评测。对已有回执按首次 EOS 返回块重新计时，速度中位数差 **+11.154%**，未新增测试请求。
- **结论**：vLLM-Ascend 可以在本机单张 910B2 上以 BF16 跑通该 DFlash2 草稿；本次两条短提示的总体连续生成收益约 10%，首 token 更慢。新环境作为实验保留，未替换默认服务。尚未做 DFlash2 全部算子耗时的 msprof / Insight 分解，不能把草稿额外耗时具体归因某一算子。
- **证据**：[复现与完整结果](../experiments/dflash2/README.md)、[逐请求与投机计数](../evidence/2026-10-20/dflash2-comparison.json)、[启动/显存/恢复记录](../evidence/2026-10-20/dflash2-runtime-evidence.json)、[固定来源与代码哈希](../evidence/2026-10-20/dflash2-source-manifest.json)。原始权重和带服务器路径的日志留在原私有目录。
